Current sync (dune-sync cron) uploads 4 tables: normal_vault_snapshots, normal_volume_daily, normal_wallet_activity, normal_yield_snapshots. Stellar isn’t natively indexed by Dune, so everything arrives via this upload path — that stays the architecture.

2 · Data plumbing — the one structural change

One unified activity table instead of many
Extend dune-sync to build normal_activity_v2: one row per completed action across ALL products, with columns
date · wallet · product (soroswap|lifi|cctp|savings|send|ramp) · direction · chain_in · chain_out · asset_in · asset_out · amount_usd · fee_usd · status · tx_hash.
Almost every chart below is a one-line query over this table. Two small companion tables: normal_cctp_ops (per-transfer status, duration, revert tool — for the ops charts) and normal_wallet_chains (per-chain provisioning counts). Savings/yield snapshots stay as they are.
  • Honesty rules baked into the sync: volume counts COMPLETED/confirmed rows only; CCTP uses the realized delivered amount where recorded (the Wave-5 work); fee_usd is the collected fee, not the quoted one, where the two differ.
  • USD conversion happens in the sync job at upload time from our own price source, stamped once — so charts never re-price history.
  • Free-plan caveat (the “plan changes in 13 days” banner): uploads and query counts are limited, which is exactly why v2 CONSOLIDATES into one wide table + two small ones rather than a table per product.

4 · One decision for you before GO

Public vs private
Dune dashboards are public. Sections A–D and F are marketing-friendly. Section E (failure rates, which routes revert, refund counts) is operationally gold but also shows the world our failure numbers. Recommendation: two dashboards — the public one gets A–D + F and the success-rate counter only; a second, unlisted one gets the full E section for us. Same tables, two dashboards, no extra sync cost. Say which you want.
