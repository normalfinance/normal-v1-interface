Guards That Said Yes

Branch feat/swap-matrix-hardening, run 7 (2026-08-27) — doc 95 Wave 6: checks that were supposed to stop you, but waved you through whenever they broke.

1 · What “failing open” means

A guard has two jobs: say no when something is wrong, and say yes when it is fine. There is a third case people forget — the guard cannot tell. A missing field, a request that timed out, a number it could not parse.

Every guard in this wave answered that third case with yes. That is the dangerous default, because it makes the check invisible exactly when it matters: the guard is silent whether it approved you or simply gave up.

The rule applied throughout this wave
“I don’t know” must never resolve to “go ahead.” Where we cannot establish that something is safe, we stop — and we say so before anything is signed, so stopping costs the user nothing but a retry.

2 · The quote that outlived its transaction

This is the one that could actually lose coins, so it gets the most space.

A LI.FI quote is not just a price. It comes with a built transaction. For Bitcoin that transaction pays into a Chainflip deposit channel — an address created for your swap, which expires. For routes on Ethereum the calldata usually carries its own deadline.

The card fetched a quote when you typed an amount, and then kept it. Press Swap forty minutes later and we executed that transaction:

you open /swap, type 0.01 BTC        → quote fetched, deposit channel opened
you get distracted for 40 minutes    → channel expires
you press Swap                       → BTC sent to an address that routes nowhere
Why the safety nets do not catch this one
There is no bridge to fail over to — the coins already left. There is no automatic refund — that only covers a CCTP swap whose USDC is sitting at your own Base address. The swap never reached a state our system tracks. This is precisely the failure that has to be prevented rather than recovered from.

The fix

The quote is now stamped with the moment it was built. On Swap:

  • Younger than 10 minutes → execute, exactly as before. Normal use is untouched.
  • Older → fetch a fresh quote first, then compare it with the number you were shown.
  • New price the same or better, or worse by under 1% → proceed silently. Asking permission for ordinary movement just trains people to click through the dialog that exists to protect them.
  • Worse by more than 1% → the card updates to the new number and stops. Pressing Swap again is your consent. Not a dead end — the button is live and the quote is fresh; it is one deliberate press.

Both decisions are a pure, tested module (lib/lifi/quote-freshness.ts, 9 tests). One case is worth calling out:

export function isQuoteStale(ageMs: number): boolean {
  if (!Number.isFinite(ageMs)) return true;   // unknown age = stale
  return ageMs >= QUOTE_STALE_MS;
}

If we do not know how old a quote is, it is stale. A missing timestamp must never read as “just now” — that would rebuild the original bug inside the fix for it.

3 · Two signatures, then a guaranteed failure

A Stellar swap through Soroswap is a Soroban transaction. Soroban fees run 0.05–0.5+ XLM. Ordinary Stellar payments cost 0.0002 XLM — about two thousand times less — and that smaller number was the only one the app held back.

Two ways it bit, both ending on-chain after you had signed (twice, on the two-signature path):

you didwhat happened
Pressed MAX on an XLM → USDC swap MAX offered everything above the account reserve and the 0.0002 fee. The swap then had to pay a Soroban fee out of money it had just spent. Guaranteed failure — the card offered an amount the transaction could not afford.
Swapped USDC on an account whose XLM sat at the reserve Plenty of USDC, no XLM to pay Soroban with. Nothing checked, so it built, prompted, signed, and failed with tx_insufficient_balance.

Now: MAX keeps the Soroban fee back, and a swap that cannot pay it is blocked at the button with “Add XLM to cover the network fee” — before any prompt. The check counts the XLM the swap itself sends, so it is right in both directions (utils/stellar-reserve.ts, 6 new tests).

4 · A transaction that offers the network nothing

Ethereum transactions state what they will pay per unit of gas. We took the higher of LI.FI's quoted price and the live network price:

const maxFeePerGas = max(BigInt(tx.maxFeePerGas ?? '0'), liveFees?.maxFeePerGas ?? 0n);

If LI.FI omitted the field and the fee lookup failed, both sides are 0 — and we signed a transaction offering to pay nothing. That is worse than an error:

Why zero is the worst of the three outcomes
It does not fail. It does not succeed. It sits — no miner will include it, and no error is ever raised, so nothing in the app can react. The user watches a swap that is neither done nor broken. We now refuse to sign and say the network fee could not be determined and that nothing was signed.

5 · The Bitcoin spend limit could be switched off by a bad quote

Wave 2 added a rule: a Bitcoin transaction may not spend materially more than the quote said. It took the limit as an optional argument, and the caller supplied it like this:

try { return BigInt(quote.action.fromAmount); }
catch { return undefined; }   // ← disables the entire check

So the one input capable of turning off the Bitcoin spend limit was a quote we could not parse. A guard whose off switch is “something went wrong” is not a guard. Both ends now refuse: the caller throws if the amount is unreadable or zero, and the signer itself refuses to sign without a limit to check against.

A related skip that is legitimate — and stays
The spend check is still skipped when not every input belongs to us: LI.FI may combine another party's UTXOs, and then “inputs total minus what came back” is not what left your wallet, so the arithmetic would be wrong rather than lenient. That path is covered by a different rule — the signer refuses to sign any input it cannot classify. Skipping a check that would compute the wrong answer is correct; skipping one because a parse failed is not.

6 · Two smaller ones on the same theme

guardfailed open becausenow
Gas-shortfall check before an ETH swap One failed balance read skipped the whole check, so a gas spike surfaced as the node's raw “insufficient funds” dump after the passkey Reads twice. The transport is already a fallback pool (Wave 4), so the retry usually lands on a different provider
Amount rounding when asking for a quote BigNumber rounds half up by default, so a typed amount could ask to swap one unit more than the wallet holds — failing for a reason shown nowhere on screen Rounds down. You can never be quoted more than you have

Typing the full balance walked past the fee reserve

MAX held back a little BTC/SOL for the network fee. Typing the same number did not — the balance check only asked “is this more than your balance?” So a typed full balance produced a swap with nothing left to pay the miner. There is now one expression for “what you can actually spend”, used by both the check and MAX, so the two cannot disagree.

7 · A blip that asked for a passkey and built a second wallet

This one is not a swap bug and it is the one I would most want fixed.

ensureChainAccount is what adds a chain to your wallet. It began by asking “what wallet does this user have?” using the best-effort lookup — which returns null when the request fails. But down that function, null does not mean “the lookup failed.” It means “this user has no wallet yet”, and that branch registers a new passkey and creates a new sub-organisation.

lookup times out  →  null  →  "no wallet yet"  →  new passkey + new sub-org
                                                    beside the one you already have

The strict variant of the same lookup exists precisely for this — it throws instead of guessing — and this call site now uses it. A dropped request becomes a failure you can retry, not a second wallet.

Same shape as the last two waves
Wave 5: an unreadable amount must not become NaN in a money column. Wave 6: an unanswered lookup must not become “this user has nothing.” In both, the bug is a failure being reformatted as data instead of being reported.

8 · Checked and deliberately left alone

Doc 95 also flagged the fee-pair route's 15-minute service window as able to broadcast an abandoned swap at a stale quote. I read it rather than patching it, and it does not need a change:

  • The route already refuses a pair with under 60 seconds of runway left.
  • More importantly, the built transaction carries a minimum output (Soroswap's otherAmountThreshold). I confirmed the whole quote object — threshold included — is what gets built into the XDR, rather than assuming it.

So a late broadcast at a moved price fails on-chain; it does not fill you at a bad rate. The exposure is a failed transaction and its network fee, not your money at a bad price. Adding a shorter window would trade a rare wasted fee for more legitimate swaps refused, which is the worse deal. Recorded in doc 95 so nobody re-opens it.

9 · How to test

If the price barely moved it just proceeds; if it moved more than 1% the card updates to the new number and waits for a second press. It must never execute the old quote.
