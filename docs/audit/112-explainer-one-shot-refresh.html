The One-Shot Refresh

Branch feat/swap-matrix-hardening, run 17 — savings deposit/withdraw updated the savings card instantly, but the drawer’s USDC lagged.

1 · What was actually happening

The savings flow does everything right: it waits for the transaction to confirm on-chain, updates its own position optimistically, and then announces on the shared balance channel (nf:activity-updated) — the same event every swap and send uses.

The gap was in the listener. The shared balance hook heard the event and made exactly one fresh read, 800ms later. But fresh reads are floored server-side — once per 5 seconds per user — and a savings action triggers several reads around the same moment (vault info, position, the activity feed). If the hook’s one read landed inside someone else’s floor window, it silently received the 15-second cache: pre-withdraw balances — and then nothing asked again until the 30-second background poll.

Why the two surfaces disagreed
The savings card runs its own account poll every 2.5 seconds, so it caught up almost instantly. The drawer depends entirely on that one-shot event read. Two surfaces, two clocks — the same disease as every bug this week, in yet another spot.

2 · The fix — and a free win

The listener now runs a bounded retry loop built from the same tested rules the post-swap gate uses: a real (non-floored) read ends the loop immediately; a floored read proves nothing, so it waits exactly the floor’s remaining time (the server reports it) and asks again — up to 3 attempts, then the background poll owns it. Worst realistic case is a few seconds, not thirty.

The free win: this hook is mounted in ~23 components, and every one of them used to fire its own fetch on every event — a herd of requests where all but the first were floored copies. The loop is now latched app-wide per event: one loop, one to three requests total, serving every surface through the shared cache. Less traffic, and no herd for the floor to feed stale copies to.

before: ~23 parallel one-shot reads → first one real, rest floored → maybe stale for 30s
after:  1 loop → real read ends it; floored read retried with exact timing → seconds

3 · Honest note on tests

The decision rules this loop uses (nextReadDelayMs, the attempt cap, the no-clobber and keep-known-balance seeds) are all already unit-tested from the earlier runs. The loop itself is thin glue inside a React effect — it is exercised by the existing suite compiling and by QA R73, not by a new unit test, because mocking SWR + window events would test the mock more than the code.
