The Day Horizon Went Dark

Branch feat/swap-matrix-hardening, run 12 — XLM and USDC not loading after the dev-server restart. Diagnosed with evidence this time, not guesses.

1 · Straight answer first: this was not my code

And this time I did not conclude that from reading diffs — I tested every layer live:

That last pair is the whole story. XLM and USDC are the only assets read from Horizon; BTC, ETH and SOL come from entirely different providers. One Stellar host is unreachable from your machine → exactly the Stellar pair goes blank, everything else loads. The restart is a red herring — it only marks when you started looking.

Why it was total, not just slow
Two things stacked. First, .env had been switched at some point from the keyed Validation Cloud Horizon to the public horizon.stellar.org (the keyed line was sitting there commented out) — so the public host was the only one configured. Second, the “last-good” snapshot that would have served your previous balances marked as stale had a 1-hour lifetime, and you were away for a few hours. Expired snapshot + dead host = blank, instead of yesterday’s numbers with a “stale” mark.

2 · The familiar shape of this bug

Doc 95 Wave 4’s rule was: no money path may depend on one provider. We built fallback pools for Base, Ethereum and Bitcoin. Stellar reads never got one — every consumer had exactly one Horizon URL, so one dead host blanked balances, account status and trustline checks across the whole app. Today that host actually died, and the app behaved exactly as the rule predicts.

3 · The fix

a) A Horizon pool, like the other chains already have

mainnet:  [ your configured Horizon (keyed) ] → [ horizon.stellar.org ]
testnet:  [ your configured Horizon ]         → [ horizon-testnet.stellar.org ]

The config now carries HORIZON_URLS (primary first, public as the safety net), and the readers walk the list until one answers:

  • the portfolio aggregate — the server read that blanked your XLM/USDC today (lib/stellar/horizon-pool.ts, 8 tests, including “primary unreachable → served by the fallback” built from today’s outage);
  • the shared account readers (fetchAccount, fetchAccountStrict, fetchTransaction) — which is what account status and trustline checks go through.
The one subtlety worth understanding
A 404 is an answer, not an outage. It means “this account is not funded” — the ledger has spoken. The pool returns zeros immediately and does not try the next host: failing over on 404 would re-ask a question that has already been answered, and make every unfunded account cost a round trip to every endpoint. Only connection failures, timeouts, 429s and 5xxs move to the next host. Pinned by a test.

b) Your .env is switched back

The keyed Validation Cloud endpoint (reachable, fast) is the primary again; horizon.stellar.org no longer needs its own line because it is the automatic fallback in code. Restart the dev server to pick this up — env values are baked in at start.

c) Stale beats blank

The last-good snapshot now lives 24 hours instead of 1. If every Horizon in the pool is ever down at once, you see your latest known balances marked stale — an outage should degrade the data’s age, never its existence.

4 · Honest notes

notedetail
Why was the keyed Horizon commented out? Unknown — the line was there, disabled, with the public host active. Worth remembering if it was deliberate (e.g. saving quota). With the pool it no longer matters much: whichever is primary, the other catches it.
The keyed URL is NEXT_PUBLIC_ That prefix ships the key to every browser. Pre-existing, and already on the infra audit list (doc: infra API keys) — not making it worse today, not fixing it today either.
Writers (submit paths) keep a single Horizon Deliberate. A submit that times out may still have landed; auto-retrying it against a second host risks double-submitting. Reads are safe to fail over; writes need the idempotent handling they already have. With the primary now reachable, submits work on your machine too.
Port 3000 curiosity While diagnosing: localhost:3000 on your machine is serving a different project entirely (a Payload template from next-websites). The Normal app is on 8082. Nothing wrong — just do not trust a :3000 tab if one is open.
