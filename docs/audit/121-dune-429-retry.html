Dune 429 Retry

2026-08-31 — the v2 tables existed but stayed empty: Dune’s free-plan rate limit was killing the last third of every sync. Run 121, branch chore/console-hygiene. Follows doc 120 (table bootstrap).

1 · What you saw, and the evidence

After the doc-120 create script (four green OKs) and a sync, the query SELECT SUM(amount_usd) FROM … normal_activity_v2 ran without error but returned a blank cell — SQL’s SUM over an empty table is NULL. Table exists, zero rows. I re-ran the sync myself against your dev server and the JSON response was the smoking gun:

"users":            "674 rows",           ← old tables fine
"transaction_log":  "323 rows",
"activity_v2":   "ERROR: Dune clear failed … 429 Too many requests. Please upgrade your plan"
"cctp_ops":      "ERROR: … 429"
"wallet_chains": "ERROR: … 429"
"holdings_snapshots": "6 rows"             ← survived — see why below
Cause → effect chain
One sync makes ~24 Dune API calls in sequence (8 old tables × clear+insert, then the 4 v2 steps). Dune’s free plan rate-limits requests per minute → the old tables, running first, spend the whole window → by the time the v2 steps fire, every call gets 429 Too many requests → the v2 clear throws, the step’s try/catch records ERROR and skips the insert → the tables stay empty → your query returns NULL. holdings_snapshots escaped because it is append-only: no clear call, one request instead of two, fired last — by then a slot had freed up. The v2 steps weren’t unlucky; they are structurally LAST in line, so they will lose this race every single run. That is why this needed a code fix, not a re-run.

2 · The fix — wait out the window instead of dying

filechange
src/lib/dune/client.tsBoth duneClear and duneInsert now go through one duneFetch with 429-aware retry: on 429, wait (Dune’s Retry-After header if sent, capped at 60s; otherwise a 5s → 15s → 30s ladder) and try again, up to 3 retries per call. A shared per-run budget caps TOTAL retry sleep at 120s so the cron can never outgrow its maxDuration = 300. The decision lives in a pure function, duneRetryDelayMs(status, attempt, retryAfterHeader, remainingBudgetMs).
src/lib/dune/client.test.tsNEW — 4 tests: the backoff ladder then give-up, Retry-After honoured and capped, non-429 never retried, budget refusal. Suite is now 518 tests / 60 suites.
src/app/api/cron/dune-sync/route.tsCalls resetDuneRetryBudget() at the start of each run — serverless instances stay warm between cron runs, so without the reset a second run would inherit a spent budget.
Deliberate choice, labelled: ONLY 429 is retried
A 429 is rejected at Dune’s gate — nothing was written, so retrying is always safe. A 5xx is different: the request MAY have committed server-side before the error, and blindly retrying an insert would then duplicate rows — deadly for the append-only holdings table, where duplicated rows double that day’s totals in every SUM. So a 5xx still fails the step loudly, exactly as before. Trade-off: a transient Dune outage still shows ERROR for that step and heals on the next daily run — honest and safe beats silently wrong.
