RPC Key Migration

2026-09-01 — moving Alchemy and Helius from your personal accounts to the company ones: which keys to create, how to lock them down, every env var to change, and how to prove it worked. Run 126, branch chore/console-hygiene.

Why you need FOUR keys, not two
Two of these variables are NEXT_PUBLIC_*, which means their value is compiled into the JavaScript every visitor downloads. Anyone can read them and spend your quota. The two server-only variables are never sent to a browser. So the right split is one restricted browser key + one unrestricted server key per provider — if you reuse a single key, you must either leave it open to the world or apply a domain allowlist that would break your server-side calls (Vercel functions send no browser Origin).

2 · Alchemy (company account)

  1. Log into the company Alchemy account → Apps → Create new app. Name it normal-web. Under networks enable Ethereum Mainnet and Base Mainnet (one Alchemy key serves several networks — you just swap the subdomain, which is exactly how your current key already serves both).
  2. Create a second app called normal-server, same two networks. This is the one whose key never leaves your infrastructure.
  3. Copy both API keys (the string after /v2/ in the app’s HTTPS URL).
  4. Lock down the browser key only: open normal-web → Security / app settings → add an allowed-domains (referrer) rule: normalfinance.io, *.normalfinance.io, your Vercel preview domain, and localhost. Leave normal-server with no domain rule — a Vercel function would be rejected by one.
  5. Set a usage alert on both apps (Alchemy → Usage → alerts) so a leak or a runaway loop pages you instead of surprising you on an invoice.

3 · Helius (company account)

  1. Company Helius dashboard → API Keys → create normal-web. In its settings add the same allowed domains list as above.
  2. Create a second key normal-server with no domain restriction — the activity feed calls Helius from the server, where there is no browser origin to check.
  3. Copy both keys. The RPC URL form is https://mainnet.helius-rpc.com/?api-key=<KEY>; the activity route uses the bare key against api.helius.xyz.
  4. Set a usage alert here too.

4 · The exact env changes

Replace these five lines in packages/web/.env (local) and in Vercel → Project → Settings → Environment Variables, for every environment you run (Production, Preview, and Development if present):

NEXT_PUBLIC_ETH_RPC_URL=https://eth-mainnet.g.alchemy.com/v2/<ALCHEMY_WEB_KEY>
NEXT_PUBLIC_SOLANA_RPC_URL=https://mainnet.helius-rpc.com/?api-key=<HELIUS_WEB_KEY>

CCTP_RPC_URL_ETHEREUM=https://eth-mainnet.g.alchemy.com/v2/<ALCHEMY_SERVER_KEY>
CCTP_RPC_URL_BASE=https://base-mainnet.g.alchemy.com/v2/<ALCHEMY_SERVER_KEY>
HELIUS_API_KEY=<HELIUS_SERVER_KEY>
Two Vercel gotchas that waste an afternoon
1. NEXT_PUBLIC_* values are baked in at BUILD time. Changing them in the Vercel UI does nothing until you redeploy — and a redeploy of the existing build is not enough if it is served from cache; trigger a fresh deployment. 2. Nothing is picked up mid-deployment either: server vars come from the deployment’s env snapshot. Rule of thumb: change env → redeploy → verify → only then disable the old keys.

These variables are all declared in turbo.jsonc’s globalEnv, so changing a value correctly invalidates the build cache — no stale bundle carrying the old key. (An env-audit test enforces that; it is why the LI.FI wallet vars had to be added there last run.)

5 · A real bug this audit found, fixed in this run

Solana sends were running on the free public node
The app reads NEXT_PUBLIC_SOLANA_RPC_URL everywhere — except the two send paths (api/send/execute broadcast and server/send-records confirmation), which read NEXT_PUBLIC_SOL_RPC_URL, a name that has never been set in your .env. Cause → effect: a user sends SOL → the broadcast goes to api.mainnet-beta.solana.com, the heavily rate-limited public endpoint → under load it throttles, and a send can fail or its confirmation probe can stall — on the one path where money is actually leaving. Your Helius quota was never used for it.

Fixed: one resolver, SOLANA_RPC_URL in lib/chains/rpc-fallback.ts, reads the current name first and the legacy name second (so a value set under either keeps working), then the public node. Both send paths now use it, and 5 tests pin the precedence so the two names cannot drift apart again. You only ever set NEXT_PUBLIC_SOLANA_RPC_URL; if NEXT_PUBLIC_SOL_RPC_URL exists in Vercel, delete it.

Then npm run dev and: open the portfolio — ETH and SOL balances must load; open DevTools → Network and confirm the requests go to the new host/key.

b) After deploying

  1. Portfolio loads ETH + SOL balances on production.
  2. Do one small SOL send — this is the path that was silently on the public node. It should confirm normally, and Helius usage should tick up.
  3. Trigger the Dune cron once; holdings_snapshots still reports rows (it reads ETH, Base and Solana through these same vars).
  4. Watch the CCTP relayer on the next cross-chain swap — mints use CCTP_RPC_URL_*.
  5. Check both provider dashboards show traffic on the company keys.

c) Only then, retire the old keys

Wait ~24h after a clean deploy, confirm the personal accounts show near-zero traffic, then delete/disable those keys. Do not skip this: the old browser key has been public in the bundle for months, so it stays spendable by anyone who saved it until you disable it.
