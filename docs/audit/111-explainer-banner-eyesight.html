The Banner That Could Not See Failure

Branch feat/swap-matrix-hardening, run 16 — why the ghost row survived run 15, in one line.

1 · Your screenshot proved the fix worked — and exposed my gap

Look at your own Activity feed: the ETH → USDC row shows Failed, $0. That is run 15’s retirement doing its job — the database row was marked FAILED with the honest detail. The banner showed the same row as “finish once it arrives” anyway, because the banner does not trust the server’s list — it fetches all recent rows and classifies them itself, with this table:

REFUNDED   → hidden
COMPLETED  → hidden
FAILED     → (no rule — falls through to "halt-receive")

Until yesterday, an inbound row with a source hash could not be FAILED — retirement was broken, which is what run 15 fixed. So the classifier never needed the line. The moment retirement started working, retired rows existed for the first time, fell through the table, and came out labelled “USDC on Base, needs the burn”.

Owning it
Run 15 taught the state machine a new terminal state and did not teach the banner’s classifier to recognise it. That is the same class of miss I have been fixing all week — two surfaces reading one fact through two private rules — and this time both rules were mine.

2 · The fix

One line — FAILED → hidden, beside REFUNDED — plus insurance against a third bite: the phase table now lives in its own pure module (cctp-phase.ts) with 9 tests, the first of which is your exact ghost (a FAILED inbound row with a source hash must be invisible). The banner imports the table instead of owning a private copy; any future state the machine learns must pass this test file to reach the banner.
