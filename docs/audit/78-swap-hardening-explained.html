The Live-Fire Round

Everything the first real days of #33 testing broke, and how each break became a structural fix · branch feat/external-wallet-cctp · 2026-08-21 · companion to docs 73 & 77

The theme of this document
Doc 77 described the autopilot as built. This document is what happened when a real user (Niko) actually used it — seven distinct failures in two days, each caught live, each fixed at the ROOT rather than patched — followed by a systematic ALL-SCENARIOS sweep (§9) that found and fixed twelve more before anything shipped. Confirmed working by live test at the end: 1-signature cross-chain swaps, the Soroswap progress popup, and fee collection verified against the database. Read this to understand not just what changed, but the recurring shapes of bug we now guard against.

1 · A leftover flag broke swaps — flags must degrade

What happened: SOROSWAP_EMBEDDED_FEE=1 was still in the dev .env from an earlier spike. Its code path calls Soroswap's fee-build endpoint — broken upstream — so every Stellar swap died with a 400.

The structural fix: the flag can no longer fail a swap, only change how many signatures it takes. The quote route wraps the embedded path in a 10-minute circuit breaker: an embedded failure retries the legacy shape in place, and the client's one-signature path runs ONLY when the response provably carries our fee — otherwise it falls through to the proven two-signature flow, fee intact. Cause-effect: Soroswap fixes their endpoint → 1-signature swaps switch on by themselves. Until then → 2 signatures, everything works.

Rule recorded: a feature flag's failure mode must be the un-flagged behavior, never an error.

2 · The consent saga: three bugs, one broken ceremony

Enabling the autopilot failed live twice, differently. The post-mortem found a chain of three defects that compounded:

  1. The policy never could be created. Our policy condition used [list].contains(eth.tx.to) — but Turnkey's .contains() only accepts a literal, never a field. The correct form is eth.tx.to in [list]. Every ceremony was doomed at step 2 from day one. The fix was validated against Turnkey's live parser before asking for another tap (a test policy created and deleted on our parent org).
  2. The ceremony wasn't idempotent. Step 1 (create the delegate user) succeeded, but our result parsing missed the userId key and threw; the retry then hit "credential public keys must be unique". Now the grant asks the server for an existing delegate and REUSES it — retries converge, and a repair takes one confirmation instead of erroring.
  3. "On" lied. Status counted only the delegate user, so the half-state (user without policy) showed On with no repair door. Active now means user AND policy exist.

Rules recorded: any ceremony a user can retry MUST be idempotent; "active" must mean the whole grant, not its first artifact; generated DSL (policy conditions) is parser-validated in a spike before shipping in a user-facing ceremony.

3 · Where the consent offer finally lives

The offer moved twice during live testing; the final shape has four doors, none blocking:

  • At swap start (the main moment): "Finish future swaps automatically?" — Enable or Not now, then the swap proceeds either way. "Not now" is remembered forever.
  • During the bridge wait: while a swap sits at "arriving/bridging" with autopilot off, the popup shows an inline "Enable auto-finish" box — enabling mid-wait completes the swap that's already running, because the engine re-checks status right before the signing step.
  • Settings → Accounts: Turn on / Turn off, honest On/Off/Unknown status.
  • After Done (backstop): offers once if somehow never offered before.

The step copy is autopilot-aware: with the delegation on, the bridge step reads "Automatic — no signature needed" and the header says "One signing step"; the "1–2 signatures" text only appears when it's actually true. The dialog copy stopped overpromising ("up to two quick passkey confirmations" — the ceremony is two stamped activities).

4 · Stellar swaps: progress popup + true Done

Stellar (XLM↔USDC) swaps were the last flow with no status popup and a fire-and-forget ending — Done showed, then the drawer needed 2–3 seconds to catch up. Now they narrate themselves in the same visual language as cross-chain swaps: Preparing → Approve (with honest per-path signature copy that follows a mid-run degrade) → Submitting → Updating balances → Done, with a stellar.expert link at the end and error + Try again in the popup.

The "Updating balances" step is the interesting one. One awaited refresh was not enough: fired right after the ledger closes, it can read Horizon's lagging replicas and "freshly" cache the PRE-swap balances. The gate now snapshots your to-asset's account total, refreshes, and if the number didn't move, waits past the server's 5-second cache floor and pulls once more — Done means every surface already shows the result, at the cost of up to ~6 extra visible seconds in the laggy case.

Rule recorded (10th instance of this disease): an awaited refresh is only half the gate — Done requires the number to have VISIBLY CHANGED, or one bounded retry past the cache floor.

5 · The gas reserve that lied about "headroom"

What happened: ETH → USDC failed pre-broadcast: balance 0.009063 ETH, transaction wanted 0.009094. The reserve held back 0.0005 ETH; the route needed 0.000531 — short by ~7 cents. Root cause: cross-ecosystem pairs reserved gas for 400k gas while plain ETH swaps reserved 550k — but both start with the IDENTICAL LI.FI deposit contract (~538k observed live; it's visible in the failing transaction's own calldata). The code comment claimed "larger headroom for the bridge" while the number was smaller.

Fix: one 550k reserve for every pair that spends ETH — reserve sizing follows the source-leg contract, not the pair's label. Also: the popup used to show the raw RPC dump for this error; the calm message ("Not enough ETH left to pay the network fee…") existed but was wired into only one engine — now both.

Funds were never at risk: the node refuses this class of transaction BEFORE broadcast; the activity row closed as Failed honestly.

6 · Dynamic gas: a spike becomes a choice

Even a correct reserve is a prediction — gas is a live market price and can spike between your quote and your click. The requirement (Niko): this must never dead-end in an error. Three layers now:

  1. The live reserve keeps ~99% of swaps away from the edge (§5).
  2. A local affordability check BEFORE the passkey ceremony: the app runs the node's own admission rule (balance ≥ amount + gas × current price) itself. A miss raises a structured signal carrying the exact amount that IS affordable — and since nothing has been signed yet, aborting is free.
  3. The choice dialog: "Network fee just went up — you can swap up to 0.00853 ETH at the current fee. Nothing was signed or sent." One tap writes the affordable amount into the card, the quote refreshes, and the user confirms the UPDATED numbers with a normal Swap press.

Two deliberate decisions, worth a junior's attention: the amount is never silently shrunk (a smaller input changes what you receive — signing a swap you never saw quoted breaks the honesty rules), and the adjusted swap is never auto-signed (passkey prompts need fresh user interaction in browsers; an auto-triggered ceremony after async re-quoting fails with NotAllowedError on some of them — the design is forced by WebAuthn, not just caution). The math has 6 unit tests pinned to the live incident's exact wei values.

7 · Small: pickers sort by value

Every asset picker (swap, send, withdraw, asset actions — all one shared component) now lists "Your assets" and search results by USD value, highest first. The zero-balance "All assets" list keeps its curated order, where a value sort would be meaningless.

8 · "Are our fees failing?" — no, verified

Asked live, answered from the database, not from confidence: every Stellar swap row carries its fee amount and a confirmed on-chain fee transaction — including the swaps made during this round. The Soroswap degrade changes only the packaging of the fee (own transaction = the second signature), never whether it's charged; LI.FI swaps collect the fee via the integrator mechanism inside the swap. The second signature IS the fee payment — two signatures means the fee definitely happened.

9 · The all-scenarios sweep — 12 findings, 12 fixes

After two gaps surfaced one live-test at a time, Niko ordered a systematic audit: "think of all possible scenarios and double check them all." Three parallel code-tracing passes walked the full matrix — wallet states × pair types × directions × missing-asset states × failure combinations — plus a dedicated security pass over the new server-side signing. Twelve gaps were confirmed; all twelve are fixed (gated: 248 tests, lint, typecheck, production build); three further low-risk items were deliberately deferred with written reasons (§11), not dropped.

The rules this sweep added to the register
1 · Any server route that moves or sends value must pin its addresses to DB-verified ownership — row contents are untrusted client input.  2 · A capability added to one engine is a requirement on every engine.  3 · A setup dialog's success must refresh the exact store its gate reads.
