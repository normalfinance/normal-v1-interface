1 · The problem

Count the passkey prompts per flow before this branch:

FlowPromptsWhy
LI.FI swap (BTC/ETH/SOL↔)1one source-chain transaction — the target we want everywhere
CCTP inbound (BTC/ETH/SOL → USDC on Stellar)2–3after the bridge (≈20 min), an approve + burn on Base needed YOUR signature
CCTP outbound (USDC → BTC/ETH/SOL)2after the mint (≈1 min–20 min), the pivot swap on Base needed YOUR signature

The second prompt is the one Niko banned: "sign, wait 20–50 minutes, sign again." Nobody waits at the screen that long — so in practice the swap stalled until the user came back, found the recovery banner, and tapped it. The requirement: one signature before the swap executes, everything after runs itself.

2 · The idea: a bounded delegation

The mid-flow signer on Base is the user's own Turnkey wallet — and Turnkey supports adding a second, restricted "user" to a wallet organization. So with ONE passkey ceremony we add:

  1. an API-only user named "Normal Autopilot" on YOUR wallet org, whose credential is our server's public key (one keypair serves all consenting users; the private half never leaves the server), and
  2. a policy that says exactly what that user may sign — and nothing else.

After that, the mid-flow Base step (gas top-up → approve → burn or pivot → receipt waits → database update) runs entirely server-side. You sign once, at the start. Bonus: closing the tab no longer matters for that step — the server finishes it.

3 · Why it's safe — the WALLET enforces it, not our server

This is the part a junior must understand: the security does not depend on our server behaving. The policy lives inside Turnkey's signer. If our server is buggy — or outright breached and the autopilot key stolen — the signer still refuses anything outside:

  • Chain: Base mainnet only (chain_id == 8453)
  • Native value: zero (value == 0 — the key can never move ETH)
  • Destination: exactly three contracts — USDC, Circle's TokenMessengerV2, LI.FI's router. The first two are imported from the same config constants the burn code sends to (they can't drift apart); the LI.FI address was verified against LI.FI's own deployment API (li.quest/v1/chains).

Cause-effect: if anything tries to sign outside these bounds → Turnkey refuses → the app falls back to asking YOU to sign. The failure mode is always a prompt, never a wrong signature.

On top of the policy, our server adds its own bounds (defense in depth, one chokepoint in autopilot-signer.ts):

BoundValueIf exceeded
Per-leg cap$2,000 (env AUTOPILOT_MAX_TX_USD)Server refuses to sign → you get the normal passkey prompt → the swap still completes, just not automatically. Every refusal is written to the audit table.
Rolling daily cap$10,000 (env AUTOPILOT_MAX_DAILY_USD)
Idle expiry90 days without use (env AUTOPILOT_IDLE_EXPIRY_DAYS)
Kill-switchAUTOPILOT_DISABLED=1ALL server signing stops instantly, app-wide, without touching anyone's wallet

And the routes themselves re-check everything the recovery banner checks, plus session ownership: it must be your transfer, in the right state, with the signer address cross-checked against your wallet row — and for the outbound pivot, the delivery address is read from your own wallet row in our database, never from the request. That last rule matters because the Turnkey policy cannot see inside LI.FI's calldata; the server-side lookup is what pins delivery to your own wallet.

4 · What actually happens during a swap now

First CCTP swap ever (per browser)

  1. You click Swap → a dialog appears before anything signs: "Finish swaps automatically?"
  2. Enable — one passkey: the ceremony runs (creates the delegated user + policy), then your swap continues normally. First time total: ceremony + the swap's own signature.
  3. Not now: the swap continues with the old prompts, the dialog never reappears (remembered in this browser), and Settings keeps a "Turn on" door.

Every swap after enabling

  1. Inbound (ETH → USDC): you sign the source-chain swap. That's it. USDC lands on your Base address → the server tops up gas, approves, burns → the bridge mints on Stellar → Done.
  2. Outbound (USDC → SOL): you sign the Stellar burn. That's it. The bridge mints USDC on your Base address → the server tops up gas and runs the LI.FI pivot → delivery tracking to your wallet as before.

The progress popup shows the same stages either way — the difference is simply which steps stop asking you to sign.

5 · The safety rules, each one testable

  • Fallback, never blockage. ANY autopilot failure — no consent, revoked, kill-switch, Turnkey down, cap hit, policy rejection, timeout — falls back to interactive prompts. Autopilot removes prompts; it never blocks a swap. (Tests J4–J7)
  • Status honesty. A failed status check reads "Unknown" in Settings and means "prompts for this run" in the engine — never treated as a revocation, never shown as a fake On/Off.
  • Race safety. The row updates are guarded (updateMany on "hash still null"), so a simultaneous recovery-banner tap can't be clobbered; the gas top-up goes through the same locked core as the manual path, so double-funding is impossible.
  • State-machine correctness. The server's burn patch also flips the row's status to BURN_SUBMITTED — without that flip the cron would never advance the bridge and the transfer would stall forever. (Caught in port review, before it could become a live incident.)
  • Audit. Every signature attempt — signed, failed, refused-cap, refused-disabled, refused-expired — is one row in autopilot_signatures, with the leg's USD amount. (Test J10)

9 · What is deliberately NOT done yet

  • v2 policy hardening (ABI arguments). Today the policy bounds chain + value + destination contracts. v2 will also make Turnkey check the ARGUMENTS — e.g. a burn's recipient must be your own forwarder, an approve's spender must be in the allowlist, and the $2k cap moves into the policy itself. This needs uploading contract ABIs to Turnkey; building it blind risks breaking the ceremony for everyone, so it waits until ONE live ceremony (J1) has proven the v1 shape. Until then the recipient rule is enforced by our server code (which only ever constructs forwarder-recipient burns) — a real but weaker guarantee, stated honestly.
  • Grant-date expiry. The 90-day idle clock starts at first USE, not at the grant itself (we don't store the grant date server-side yet). v2 item.
  • Testnet autopilot. The policy allows Base mainnet only. On testnet the autopilot simply declines and you sign manually — fine, since LI.FI has no testnet liquidity anyway.

10 · The other half of #33 — Soroswap single-signature (blocked upstream)

Stellar-only swaps (XLM↔USDC) and savings still take 2 signatures, because a Soroban transaction holds exactly one operation — our fee can't ride inside the swap. The fix is implemented and dormant: Soroswap's API supports an embedded fee (feeBps + referralId), our code is complete behind SOROSWAP_EMBEDDED_FEE=1, but their build endpoint currently 400s with the fee attached (proven with a control test; repro sent upstream — doc 76 §7). The moment Soroswap fixes it, flipping one env delivers 1-signature Stellar swaps with zero code changes. Savings need Stage 2 (the Normal router contract) — designed, not started.
