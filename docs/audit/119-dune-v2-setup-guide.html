2 · One-time setup (15 minutes)

  1. API key: dune.com → Settings → API → create a key. It already exists if the current dashboard updates (the sync uses it today). Env vars on Vercel: DUNE_API_KEY, and DUNE_NAMESPACE only if your team handle is not normalfinance.
  2. Create the four new tables first — Dune’s insert/clear API returns 404 for a table that was never created, so the sync cannot make them appear on its own (that is exactly the “Table … does not exist” error in the query editor). One-time bootstrap, same as the original 8 tables (doc 120 explains):
    cd packages/web
    .\scripts\create-dune-tables-v2.ps1 -ApiKey "<DUNE_API_KEY from .env>"
    Expect four green OK lines: normal_activity_v2, normal_cctp_ops, normal_wallet_chains, normal_holdings_snapshots.
  3. Run one sync by hand to fill the tables before you build queries. No deploy needed for this: localhost works, because the dev server runs this branch, the local .env has the Dune key, and localhost shares the production database — so real data uploads. Your usual command:
    Invoke-RestMethod -Uri "http://localhost:8082/api/cron/dune-sync" -Method GET -Headers @{ Authorization = "Bearer <CRON_SECRET>" }
    (After the merge, the deployed cron takes over — that is what makes the DAILY holdings history accumulate without manual runs.)
    The JSON response lists row counts per table — activity_v2, cctp_ops, wallet_chains, holdings_snapshots should all show rows, not ERROR. The call can take ~3 minutes: one sync makes ~24 Dune API calls, the free plan rate-limits per minute, and since doc 121 a rate-limited call waits out the window and retries instead of failing with 429.
  4. Smoke-check in Dune: New Query → SELECT * FROM dune.normalfinance.normal_activity_v2 LIMIT 20 → Run. You should see soroswap, lifi, cctp, savings rows side by side.

3 · The queries — paste each into a New Query, add the visualization, Save

For every block: Dune → New Query → paste → Run → New visualization → set the type/fields shown in blue → rename the query to the title → Save. The italic line under each heading is that query’s plain-language description — paste it into the query’s Description field in Dune (it shows on hover) or add it as a text widget next to the chart on the dashboard.

3.1 Total volume, all-time Counter

Every dollar that has moved through Normal since launch — all three swap engines (Soroswap, LI.FI, CCTP), savings deposits and withdrawals, sends, and on/off-ramps. Completed actions only. This is a FLOW number: it only ever grows.

SELECT SUM(amount_usd) AS total_volume_usd
FROM dune.normalfinance.normal_activity_v2
WHERE status = 'completed';

3.2 Total protocol fees, all-time Counter

Everything Normal has earned, all time: Soroswap 0.5% swap fees, CCTP swap fees, LI.FI integrator fees, and savings deposit fees.

SELECT SUM(fee_usd) AS total_fees_usd
FROM dune.normalfinance.normal_activity_v2
WHERE status = 'completed';

3.3 Fee revenue by product Pie/Donut — label: product, value: fees_usd

The same all-time revenue, split by product — which product actually earns.

SELECT product, SUM(fee_usd) AS fees_usd
FROM dune.normalfinance.normal_activity_v2
WHERE status = 'completed' AND fee_usd > 0
GROUP BY 1 ORDER BY 2 DESC;

3.4 Daily fee revenue by product Bar — X: day, Y: fees_usd, stack by product ("Enable stacking")

Revenue per day, stacked by product — what is earning NOW, not just historically.

SELECT date_trunc('day', CAST(date AS timestamp)) AS day,
       product, SUM(fee_usd) AS fees_usd
FROM dune.normalfinance.normal_activity_v2
WHERE status = 'completed'
GROUP BY 1, 2 ORDER BY 1;

3.5 Cumulative revenue Area — X: day, Y: cumulative_fees

All-time earnings as a running total — the up-and-to-the-right line.

WITH daily AS (
  SELECT date_trunc('day', CAST(date AS timestamp)) AS day, SUM(fee_usd) AS fees
  FROM dune.normalfinance.normal_activity_v2
  WHERE status = 'completed' GROUP BY 1
)
SELECT day, SUM(fees) OVER (ORDER BY day) AS cumulative_fees FROM daily ORDER BY day;

3.6 Daily volume by product Bar — X: day, Y: volume_usd, stack by product

Dollars moved per day, stacked by product — the day-to-day picture of what people actually use.

SELECT date_trunc('day', CAST(date AS timestamp)) AS day,
       product, SUM(amount_usd) AS volume_usd
FROM dune.normalfinance.normal_activity_v2
WHERE status = 'completed'
GROUP BY 1, 2 ORDER BY 1;

3.7 Product mix, all-time Pie/Donut

Share of all-time volume by product.

SELECT product, SUM(amount_usd) AS volume_usd
FROM dune.normalfinance.normal_activity_v2
WHERE status = 'completed'
GROUP BY 1 ORDER BY 2 DESC;

3.8 Top swap routes, all-time Bar, horizontal — Y: route, X: volume_usd

The most-traded pairs since launch — which conversions people actually make (XLM↔USDC, USDC→ETH, BTC→USDC…).

SELECT asset_in || ' → ' || asset_out AS route,
       SUM(amount_usd) AS volume_usd, COUNT(*) AS swaps
FROM dune.normalfinance.normal_activity_v2
WHERE status = 'completed' AND action = 'swap'
GROUP BY 1 ORDER BY 2 DESC LIMIT 15;

3.9 Daily active wallets Line

Unique wallets that completed at least one action that day, across ALL products. (The old chart counted Stellar activity only.)

SELECT date_trunc('day', CAST(date AS timestamp)) AS day,
       COUNT(DISTINCT wallet_address) AS active_wallets
FROM dune.normalfinance.normal_activity_v2
WHERE status = 'completed'
GROUP BY 1 ORDER BY 1;

3.10 Wallets by chain (cumulative) Area — X: day, Y: wallets, stack by chain

How many wallets hold each chain address over time — multi-chain (Turnkey) adoption.

SELECT date_trunc('day', CAST(date AS timestamp)) AS day, chain,
       SUM(SUM(wallets_added)) OVER (PARTITION BY chain
         ORDER BY date_trunc('day', CAST(date AS timestamp))) AS wallets
FROM dune.normalfinance.normal_wallet_chains
GROUP BY date_trunc('day', CAST(date AS timestamp)), chain ORDER BY 1;
TVL vs. volume — the distinction, once
Volume (3.1, 3.6) counts flows: every swap on every engine, every deposit, withdrawal, send and ramp — it includes all the swaps and only ever grows. TVL (3.11, 3.12) counts holdings: what sits in users’ wallets plus the savings vault at a moment in time. Swaps do not add to TVL — they convert one held asset into another, and the result is already counted in the holdings snapshot. Savings IS included in TVL, as its own stacked band.

3.11 Combined TVL over time Area — X: day, Y: usd, stack by bucket

What users HOLD on Normal at each point in time: every known wallet’s balances (BTC, ETH, SOL, XLM, USDC) plus the savings vault, stacked. A STOCK number — it falls when people withdraw or send out.

WITH runs AS (
  SELECT snapshot_date,
         CASE WHEN asset = 'SAVINGS' THEN 'Savings (DeFindex)'
              ELSE 'Wallet holdings' END AS bucket,
         SUM(usd_total) AS usd
  FROM dune.normalfinance.normal_holdings_snapshots
  GROUP BY 1, 2
), ranked AS (
  SELECT date_trunc('day', CAST(snapshot_date AS timestamp)) AS day, bucket, usd,
         row_number() OVER (PARTITION BY date_trunc('day', CAST(snapshot_date AS timestamp)),
                            bucket ORDER BY snapshot_date DESC) AS rn
  FROM runs
)
SELECT day, bucket, usd FROM ranked WHERE rn = 1 ORDER BY day;

Why the ranking: the holdings table is append-only and each run stamps its full time, so running the sync several times in one day (normal during setup) is harmless — this query keeps only the latest run per day.

This is savings TVL + everything users hold in their wallets, stacked — “TVL combining all”. It grows from deploy day; the old savings-only chart (existing normal_vault_snapshots query) can stay beside it for deep history.

3.12 Current combined TVL Counter

One number: everything users hold right now — all wallets plus savings.

SELECT SUM(usd_total) AS combined_tvl_usd
FROM dune.normalfinance.normal_holdings_snapshots
WHERE snapshot_date = (SELECT MAX(snapshot_date)
                       FROM dune.normalfinance.normal_holdings_snapshots);

3.13 Total holdings by asset, right now Bar, horizontal — Y: asset, X: usd_total

ALL wallets combined, per asset: how much BTC, ETH, SOL, XLM, USDC and savings people hold at this moment — token amounts and USD side by side.

SELECT asset, SUM(balance_total) AS balance, SUM(usd_total) AS usd_total
FROM dune.normalfinance.normal_holdings_snapshots
WHERE snapshot_date = (SELECT MAX(snapshot_date)
                       FROM dune.normalfinance.normal_holdings_snapshots)
GROUP BY 1 ORDER BY 3 DESC;

3.14 Keepers

Total registered users, signups over time, savings TVL history, total yield — the existing queries stay exactly as they are.

  2. Add text widgets as section headers: Growth · Volume · Revenue · TVL & Holdings · Savings.
  3. Add visualization → pick each saved query. Suggested order: Row 1 counters — users · total volume (3.1) · total fees (3.2) · combined TVL (3.12). Row 2 — daily volume by product (3.6) · product mix (3.7). Row 3 — daily fees (3.4) · fee donut (3.3) · cumulative revenue (3.5). Row 4 — combined TVL area (3.11) · holdings-now bar (3.13). 5 · Reliability queries — ready when you want them (public-URL caveat above)

Reliability, from the CCTP ops table: how often bridges complete, how long they take by direction, and which LI.FI bridge/DEX reverts most — the chart that would have exposed the “fly” incident at a glance.

-- Success rate, all-time (Counter)
SELECT ROUND(100.0 * SUM(CASE WHEN status='COMPLETED' THEN 1 ELSE 0 END) / COUNT(*), 1)
  AS success_rate_pct FROM dune.normalfinance.normal_cctp_ops;

-- Transfers by final status per week (Bar, stack by status)
SELECT date_trunc('week', CAST(created_at AS timestamp)) AS week, status, COUNT(*) AS transfers
FROM dune.normalfinance.normal_cctp_ops GROUP BY 1,2 ORDER BY 1;

-- Median completion time by direction (Bar)
SELECT direction, approx_percentile(duration_seconds, 0.5) / 60.0 AS median_minutes
FROM dune.normalfinance.normal_cctp_ops WHERE duration_seconds IS NOT NULL GROUP BY 1;

-- Which routes revert (Bar, horizontal)
SELECT COALESCE(revert_tool, 'unknown') AS tool, COUNT(*) AS reverts
FROM dune.normalfinance.normal_cctp_ops WHERE revert_tool IS NOT NULL OR revert_exchanges IS NOT NULL
GROUP BY 1 ORDER BY 2 DESC;
