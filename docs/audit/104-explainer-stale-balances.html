The Balance That Would Not Move

Branch feat/swap-matrix-hardening, run 9 — the stale balance you hit after two Stellar swaps in a row.

1 · First: this was not one of my changes

You asked directly, so the answer first, with how I checked it.

The refresh after a swap runs through exactly three places:

refetchStellarAfterSwap  (swap-card.tsx)
   → refreshFresh()      (use-wallet-balances.ts)
      → GET /api/wallet/portfolio?refresh=1

Against develop, this branch changed none of them. use-wallet-balances.ts and the portfolio route have no diff at all; swap-card.tsx was edited, but only the double-funding guard and the amount input — not the refresh. My Stellar-side work this week was the XLM fee gate and MAX.

The bug is older than the branch. It is also real, and now fixed.

2 · Why it happened

The floor

When a swap finishes, the app asks the server for balances with refresh=1, meaning “skip your cache, go and read the chains.” That bypass is floored to once every 5 seconds per user, so it cannot be used to hammer the chain providers. Sensible.

But look at what happens to a request that arrives inside those 5 seconds:

if (!wantsFresh || withinFloor) {
  const cached = await redis.get(cacheKey);   // ← the 15-second cache
  if (cached) return NextResponse.json({ success: true, ...cached });
}

It does not wait, and it does not say no. It silently returns the 15-second cache — which can easily be from before your swap. And the response looks exactly like a fresh one. The client had no way to tell them apart.

The guess

Not being able to tell, the client guessed — by checking whether the number had moved:

const before = total(currentAssets);
const fresh  = await refreshFresh();
if (fresh && total(fresh) === before) {      // "unchanged? then it must have been stale"
  await sleep(5600);                        // wait past the floor
  await refreshFresh();                     // and try once more
}

That asks “did the number change?” as a stand-in for “was that read fresh?” Usually the same. Not always — and the case where they differ is precisely two swaps in a row.

Your two swaps, step by step

#what happened
1USDC → XLM finishes. Several refresh=1 calls fire within a second of each other (the activity-feed handler, plus the swap's own). One does the real read; the others land inside its floor and get the cache. The screen ends up still showing the pre-swap-1 figure.
2You immediately run XLM → USDC. Its before is read from the screen — so before is that stale pre-swap-1 number.
3Swap 2 finishes, its read is floored, and the cache it gets back holds post-swap-1 data. Compared with before, the number has changed.
4So the retry never runs. The balance moves to post-swap-1 and stops there. Nothing else asks again for 30 seconds, and the value it would find is already cached — so it stays wrong until you reload the page.
The one-line version
The retry existed and was correct for one swap. Two swaps made the “did it change?” signal lie — it changed to the wrong number, which the code read as success.

3 · The fix: stop guessing, ask

The server always knew whether it served a real read or its cache. It simply never said so. Now it does:

return NextResponse.json({
  success: true,
  ...cached,
  floored: !!(wantsFresh && withinFloor),   // "you asked for fresh; you got the cache"
});

And the client asks the real question instead of the proxy one. The decision is a pure, tested function:

if (attempt >= max)  return false;   // bounded — never loop at the chain sources
if (floored)         return true;    // we read nothing new; this attempt proved nothing
return !changed;                     // fresh, but the chain's replicas can lag a moment

Note the ordering. floored is checked before the number is considered at all — because a floored response tells you nothing about anything, whatever its contents say. That is the exact mistake being repaired.

Three attempts, not one

One retry was enough when only one read could be floored. Now the loop runs up to three reads, waiting 5.6 seconds (just past the floor) between them, and stops the moment it gets a genuinely fresh read showing the new value. Worst case is about 11 seconds; after that it defers to the normal 30-second background refresh rather than hammering the chains.

Both paths, one rule
The identical guess existed in refetchChain — the BTC/ETH/SOL version, used after cross-chain swaps and wallet setup. Both now call the same tested helper, so they cannot drift apart. Bitcoin and Ethereum swaps take minutes, so their reads are naturally spaced past the floor and this was much harder to hit there — but the flaw was the same, and it is fixed in both.

One smaller thing

A floored response was also being written into the browser's stored snapshot as though it were current. The transport flag is now stripped before that write, so a stale copy can never be read back later as if it described fresh data.

4 · So — is it broken for all swaps?

It was the same code path for every swap, because there is one shared balance refresh. But how easily you hit it depended entirely on timing:

swap typeexposure
Two Stellar swaps back to back Very likely — they finish in seconds, so their reads land inside one another's 5-second floor. This is what you hit.
A single Stellar swap Usually self-healed: the number was genuinely unchanged, so the one retry fired.
CCTP / LI.FI swaps Rarely — they take minutes, so consecutive reads are far outside the floor.
