2 · The cause — my gap, in one sentence

Dune’s upload API has three endpoints — create, insert, clear — and our sync only ever calls the last two (packages/web/src/lib/dune/client.ts). Insert and clear never create a table; they return 404 if it was never created. The 8 original tables exist because a one-time bootstrap script (packages/web/scripts/create-dune-tables.ps1) POSTed their schemas once, back when the first dashboard was built. When I shipped the four v2 tables, I wired the sync and wrote the queries — but never shipped the matching create step. So:

Cause → effect chain
If the table was never created → the sync’s duneClear('normal_activity_v2') gets a 404 → the try/catch records activity_v2: "ERROR: Dune clear failed … 404" in the sync response and skips the insert → nothing is ever uploaded → the Dune query editor truthfully says the table does not exist. The old tables keep working because they were created years-of-runs ago — which is exactly why one screenshot worked and the other errored.

You can confirm this was already happening: look at the JSON your Invoke-RestMethod call returned — the four v2 keys will say ERROR: … 404 while the old keys show row counts.

3 · The fix shipped this run

filechange
packages/web/scripts/create-dune-tables-v2.ps1 NEW — one-time bootstrap for the four v2 tables, an exact mirror of the v1 script: same endpoint, same auth, same error reporting. Schemas are copied field-for-field from the row interfaces in src/lib/dune/activity-v2.ts (14 columns for activity_v2, 11 for cctp_ops, 4 for wallet_chains, 7 for holdings_snapshots).
docs/audit/119-dune-v2-setup-guide.html Setup section gained the missing first step: run the create script before the first sync; the sync step no longer claims it creates tables.
Deliberate non-change, labelled
I did not make the cron auto-create tables on 404. The create endpoint needs an explicit column schema either way (it cannot be inferred from rows), so auto-create would duplicate the schema knowledge inside the cron for a case that occurs exactly once per table’s lifetime — and a loud ERROR: … 404 in the sync response is the honest signal that bootstrap was skipped. This matches how the original 8 tables work. Trade-off: any future new table needs its create step added to the v2 script first, or its sync step will 404 the same way — that rule is now written at the top of the script.

4 · What you run now (2 minutes, in order)

  1. Create the tables (key is DUNE_API_KEY in packages/web/.env): 
    cd packages\web
.\scripts\create-dune-tables-v2.ps1 -ApiKey "<DUNE_API_KEY>"
    → you will see four green OK lines. (A repeat run later would show FAILED “already exists” — harmless.)
  2. Fill them — your usual sync call against the running dev server: 
    Invoke-RestMethod -Uri "http://localhost:8082/api/cron/dune-sync" -Method GET `
  -Headers @{ Authorization = "Bearer <CRON_SECRET>" }
    → the response now shows row counts (not ERROR) for activity_v2, cctp_ops, wallet_chains, holdings_snapshots.
  3. Re-run the failing query in Dune — it returns numbers now. Continue with doc 119 section 3 as written.
