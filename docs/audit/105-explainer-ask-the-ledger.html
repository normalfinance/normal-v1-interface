1 · What I got wrong twice

Your question — “didn't we have it so it's spinning in the popup until the new balance is refetched?” — is the right one. That is the design. The popup has an “Updating balances” step and Done is supposed to wait for it.

My first two attempts both assumed that gate was sound and went hunting in the caching layers underneath it. I found two genuine bugs there and fixed them, and I was measuring the wrong thing each time. This round I looked at the gate itself, and it had three separate problems — one of which I made worse.

2 · Hole 1: one failed read skipped the entire wait

This is almost certainly what you were seeing, and it is my fault.

The balance fetch throws on any unhappy response:

if (!res.ok) throw new Error(`portfolio ${res.status}`);

My retry loop called it without catching. So a single hiccup — a rate limit, an auth refresh, one bad response — threw straight out of the loop, out of the whole gate, and landed in the engine's catch-all:

await Promise.race([
  refreshAggregate?.().catch(() => {}),   // ← swallowed here
  new Promise((r) => setTimeout(r, 15_000)),
]);
setSwapStage('done');                     // ← so Done fires IMMEDIATELY
And I made it more likely
Going from one retry to three tripled the number of requests that could throw. So the change I made to fix the stale balance also increased the chance of the gate being skipped altogether — which looks exactly like “the fix did nothing”. A failed read is simply “not fresh yet”; it now counts as a failed attempt and the loop carries on.

3 · Hole 2: it watched one balance out of two

A swap moves two balances — the one you spend and the one you receive. The gate only watched the destination. Watching both is strictly more evidence for no extra cost, and it is also what the card actually shows you. Now it waits on the pair.

4 · Hole 3: it was asking the wrong question — the real fix

Both previous rounds kept the same underlying approach: refresh the balance and see if the number moved. Step back and that is a guess about two different things at once:

if the number has not moved, is it because…then the right move is
the server handed us a cached copywait for its cache window and ask again
Horizon has not ingested the swap yetwait for the ledger, then ask once

One signal, two very different causes, and no way to tell them apart. That is why each fix helped a bit and none of them finished the job.

The question that is actually definite

The swap hands us its transaction hash. So instead of inferring from balances, we can ask the ledger directly: do you have this transaction?

await awaitTxVisible(config.HORIZON_URL, hash);   // then refresh balances

That read goes straight to Horizon — no server response cache, no bypass floor, no SWR. None of the layers that made the old signal unreliable are in the way. Once it answers yes, the ledger provably contains your swap, so the balance read that follows is being made at a moment when the right answer exists.

Cost in the normal case: nothing
Horizon has the transaction almost immediately, so this returns on the first poll. It is bounded at 8 seconds and never throws — a swap that has already succeeded must never be held up by our own bookkeeping, so if Horizon is unreachable it gives up and lets the refresh proceed as before. 7 tests, including “always takes at least one look” and “gives up inside the budget”.

5 · So the popup now genuinely waits

The sequence for a Stellar swap is now:

1. submit the swap, get a hash
2. wait until Horizon has that transaction          ← new, usually instant
3. refresh balances, retrying if the server served a cached copy
   (waiting only the remaining floor time, capped at 12s)
4. Done — with the balance on screen already updated

Step 3 keeps everything from the last two rounds: the server reports whether it floored a request, and the retry waits precisely as long as the floor has left.

6 · If it still misbehaves, the next report is an answer

I have stopped guessing in a second sense too: the gate now writes one line to the browser console per attempt.

[balance-gate:USDC->XLM] attempt 1 floored=false changed=true before=XLM:42.1|USDC:15.0
                          after=XLM:57.3|USDC:0 retryAfterMs=- elapsed=812ms

That single line distinguishes every case we have been guessing between: whether the server floored us, what it actually returned, whether it moved, and how long it took. If the balance ever lags again, open the console (F12), run one swap, and send me those lines — that turns the next round into a diagnosis instead of a fourth attempt.
