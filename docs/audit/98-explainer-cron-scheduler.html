The Crons Never Ran

Branch feat/swap-matrix-hardening, run 3 (2026-08-27). The scheduled jobs that finish bridges and collect fees have never executed — here's the evidence, the cause, and the fix.

1 · What a cron is, and why we have four

A cron is just "run this code every N minutes". Blockchain work needs it because steps can't all happen at once: you burn on one chain, wait for the network to confirm, then mint on the other. Something has to be awake to do the second half.

jobeverywhat it doeswithout it
cctp-advance2 min Drives the bridge: burn confirmed → get Circle's attestation → mint → complete The bridge stalls. Only your open browser tab does this today
fee-escrow-sweep2 min Submits the 0.5% fee held in escrow when it couldn't go out inline Our fees are never collected — silent revenue loss
ramp-reconcile5 min Clears abandoned Buy/Sell checkouts, detects arrivals with no tab open Pending banners linger (already worked around in the read path)
dune-sync4 h Pushes metrics to the Dune dashboardStale analytics only

2 · The evidence

Every cron stamps a heartbeat into Redis when it finishes. Reading those keys directly:

cctp-advance       NEVER RUN
fee-escrow-sweep   NEVER RUN
ramp-reconcile     NEVER RUN
dune-sync          2026-08-24T21:13:03Z   (2.7 days ago)
What this means
Three of the four jobs have never executed once, in any environment. Every CCTP bridge this app has ever completed was finished by a user's browser tab staying open — which is exactly why the 12 USDC had to be minted by hand, and why doc 95's "the tab is load-bearing" finding is the operating reality rather than a theoretical risk.

4 · The discovery that changes the plan

Production's cron would cover staging too
The cron reads the database, not the deployment. advancePendingTransfers() selects every pending transfer with no environment filter, and each row carries its own network field which the code follows. Since staging and production share one Supabase database, merging develop → master gives both environments working crons — production's scheduler would pick up and finish staging-created bridges.

The catch: production's cron runs production's code. Any NEW cron logic — like Wave 1's server-side pivot — only takes effect once it is on master. So merging fixes today's stalling; it does not let you test tomorrow's cron changes on staging first.

5 · What shipped: an external scheduler

.github/workflows/cron-scheduler.yml — a GitHub Actions workflow that calls the same endpoints on a schedule, from outside Vercel. It works for staging and production, independent of Vercel's preview limitation and of whatever silenced dune-sync.

  • Runs every 5 minutes (GitHub's minimum), plus a manual "Run workflow" button with a staging / production / both selector.
  • Prints each job's heartbeat stamp in the run log, so one glance answers "did it work?".
  • Fails loudly when it does nothing. If no base URL is configured it errors instead of reporting success — silence must never look like health (that rule cost us a week of ghost banners).
  • The endpoints are idempotent and secret-protected, so running alongside Vercel's own crons is safe.

Setup — repo → Settings → Secrets and variables → Actions

Cost — read before enabling on a private repo
GitHub bills Actions per minute and rounds each run up to a whole minute. Every 5 minutes is ~8,600 minutes/month, well past the free allowance on a private repo. If that matters, either raise the interval to 15–30 minutes (bridges settle a little later) or use a free HTTP scheduler instead — cron-job.org (1-minute granularity, supports the Authorization header), Upstash QStash schedules (we already use Upstash), or a second Vercel project whose Production Branch is develop. The workflow is the fastest path; it is not the only one.

6 · How to verify it's alive

  1. Add the secrets, then Actions → "Cron scheduler" → Run workflow → target staging. The log should show three ✅ lines with fresh heartbeat timestamps.
  2. Wait ~10 minutes without touching anything, then re-read the heartbeats. If the timestamps moved on their own, the schedule is live.
  3. The real proof: start a CCTP swap on staging, close the tab after signing, and come back later. The transfer should have completed without you.
