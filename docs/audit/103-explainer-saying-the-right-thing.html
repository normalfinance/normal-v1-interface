Saying The Right Thing

Branch feat/swap-matrix-hardening, run 8 (2026-08-27) — doc 95 Wave 7, the last one: nothing here loses money, but the app was telling people things that were not true.

1 · The headline: a message that rewrote itself into bad advice

You run out of ETH for gas. The app works that out correctly and says:

"Not enough ETH left to pay the network fee — try a slightly smaller amount."

That sentence is right and it is actionable. Then the progress popup ran its own second classifier over it, and one of that classifier's patterns was the bare word network:

if (/timeout|timed out|network|fetch/i.test(raw)) {
  return t('The network did not answer in time. Nothing is lost — try again in a moment.');
}

So what you actually saw was:

"The network did not answer in time. Nothing is lost — try again in a moment."
Why this is worse than showing nothing
It tells you to retry. Retrying cannot possibly work — you still do not have the ETH. So the user tries again, fails again, and now distrusts the app rather than topping up their gas. A wrong message does not just fail to help; it actively sends someone down a road with no end.

The real cause: the same job done twice

The engine already turns errors into human sentences before the popup ever sees them (the shared classifier in utils/errors/error-classifier.ts). The popup then did the job again with a sloppier copy of the rules. The shared one gets this right — its connectivity pattern requires actual failure words (timed out, failed to fetch), never the word “network” on its own.

So the popup now does not re-classify at all. It keeps exactly one rule, the only thing the shared classifier cannot know:

on-chain rejection  →  "The exchange route failed on the provider side — your USDC is
                        safe in your own account. You can retry, or bring it back as USDC."
everything else     →  shown exactly as written

That decision is now a tested module (cctp-failure-copy.ts, 5 tests), and one test is the exact sentence from this bug — so this specific collision cannot come back.

2 · A step that succeeded, marked with a red error

When you fund a swap from Lobstr, the popup lists the steps and marks the failing one in red. The code set the stage to funding, moved your USDC… and then left the stage on funding while it created the swap record on our server.

If anything in that step failed — a dropped request, a rejected record — the red marker landed on the funding step:

Moving USDC from Lobstr   ✕  <- this SUCCEEDED. Your USDC did move.
Preparing the bridge          (never reached)
Why this matters more than it looks
The user is told the money did not leave their wallet, while it has. Anyone sensible then goes looking for missing funds, or funds it a second time. The fix is one line — advance the stage the moment funding succeeds — so the marker always lands on the step that actually broke, and the funding step keeps its green check.

3 · A button that did nothing at all

“Bring back as USDC” returns USDC that is sitting at your own address on Base. It was offered on any outbound failure, including failures that happen before any USDC has reached Base — a funding failure, a failed record creation.

In those cases there is nothing to bring back. Worse, when the swap had failed before its record existed, the handler hit this:

const failedId = getActiveCctpTransfer() ?? lastFailedRunIdRef.current;
if (!failedId) return;   ← click does nothing. No error, no feedback.

A dead control, on a failure screen, which is the worst possible place for one: the user is already worried, presses the button offering to recover their money, and nothing happens. It is now shown only when both things are true — the USDC has actually reached Base (stage topup onward), and a real transfer record exists for the refund to act on.

4 · A missing setting that switched off the lock

All four scheduled jobs were written like this:

if (CRON_SECRET) {
  ...check the Authorization header...
}

Read it closely. If CRON_SECRET is not set, the check does not fail — it is skipped, and the endpoint is public. These jobs advance bridges, sweep escrowed fees and reconcile ramps. An absent environment variable silently turned money-moving endpoints into open ones, and nothing anywhere said so.

The pattern, one more time
This is the same shape as all of Wave 6: not knowing must not resolve to yes. Here the app did not know whether the caller was allowed, so it let them in.

The decision is now a pure, tested function (server/cron-auth.ts, 6 tests):

situationanswer
Secret set, correct tokenrun
Secret set, wrong/missing token401 Unauthorized
Secret not set, in production 503 — “refusing to run an unauthenticated cron”, logged
Secret not set, on a developer machinerun (localhost stays usable)

503 rather than 401 on purpose: the caller did nothing wrong, the deployment is misconfigured, and that should be fixed rather than retried. Your scheduler already sends the secret, so nothing changes for it.

5 · One cookie, sixteen routes, two different answers

Which network a request is on comes from a cookie called normal-network. Sixteen API routes read it, and each supplied its own fallback for when it is missing:

cctp/quote, cctp/transfers, send/execute   →  'mainnet'
swap/quote, savings/*, fees/*, transaction →  'testnet'

The cookie is only written once the browser store loads or you toggle the network — so on a first visit it is absent, and the same user's swap quote was built on testnet while their CCTP transfer record was created on mainnet. That is not a cosmetic split; those two must agree or the swap is nonsense.

The browser's own answer comes from one function, getCurrentNetwork(), which reads NEXT_PUBLIC_NETWORK. All sixteen routes now derive their fallback from that same function, so client and server agree by construction rather than by sixteen literals staying in step. It is the rule you already set for chain values, applied to the deployment's network.

A second thing that fixes
The old code also wrote cookie.value as NetworkType — a cast, which in TypeScript means “trust me”, not “check this”. A junk cookie value went straight through as if it were a real network. The shared parser validates instead, and returns null so the caller falls back deliberately (utils/network-value.ts, 3 tests).

6 · An escape hatch that could be left open silently

The fly DEX blocklist — the one that stops quotes routing through the fake TSLA token that burned three bridges — is disabled by setting LIFI_DENY_EXCHANGES="". That is a deliberate escape hatch and it stays.

The problem was the silence. An empty string is also exactly what an environment dashboard produces when someone clears a field, and nothing anywhere would have said the protection was off. It now logs a warning naming what is unprotected, every time. The hatch is kept; the silence is not.

7 · Checked, and doc 95 was wrong

Doc 95 listed the fee-pair flow's 40-second give-up as having “no reconciliation” — meaning that if we stop waiting for a transaction, nothing ever settles the record.

I read the code rather than fixing it, and that is not the case. There is a reconciler: reconcileTxRecords() probes every non-terminal record and settles it as confirmed, failed or abandoned. It is called by the fee-escrow-sweep job.

But there is a real history here
fee-escrow-sweep is one of the jobs we proved had never run. So the reconciliation existed and simply never happened — which looks identical from the outside. That is fixed by the scheduler already on master, and by the crons that arrive when develop reaches master. No code change needed here; the correction is recorded in doc 95 so nobody re-opens it.
