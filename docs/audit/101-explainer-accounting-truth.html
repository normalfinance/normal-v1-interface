What Actually Arrived

Branch feat/swap-matrix-hardening, run 6 (2026-08-27) — doc 95 Wave 5: the app must report the amount that really landed, not the amount we promised.

1 · The idea, in one sentence

Every quote contains two different numbers, and we were storing the wrong one.

numberwhat it meansknown when?
toAmountMin — the guaranteed minimum “you will get at least this much” — the worst case the route promises Before the swap. It is a promise.
receiving.amount — the delivered amount what the destination wallet actually received After the swap. It is a fact.

Routes almost always deliver a bit more than the minimum (that gap is the slippage buffer going unused). We recorded the promise and then guarded it against being replaced — so the Activity feed and the Dune dashboard under-reported every single swap, permanently, by whatever the route beat its own promise by.

2 · Why the guard existed, and why it was wrong here

The rule in the PATCH route was set-once: if (body.dstAmount && !transfer.dstAmount) — “write it only if it isn’t already written.” That rule is genuinely good, and it is there for a reason: several things can report on the same swap (your tab, the recovery banner, the server), and without it a late straggler could overwrite a good value with a stale one.

But the guard couldn’t tell the difference between two reports of the same kind and an estimate being corrected by a fact. The estimate always arrives first — so the fact was always the one rejected.

The fix — a second, deliberately different door
The set-once dstAmount field is untouched. A new field, dstAmountFinal, writes the same column but is allowed to overwrite, and it is only ever sent from one place: after the bridge itself has reported the destination as delivered. Estimates still can’t fight each other; a confirmed fact now wins over an estimate. 
if (body.dstAmountFinal && /^\d+(\.\d+)?$/.test(String(body.dstAmountFinal))) {
  data.dstAmount = String(body.dstAmountFinal);   // overwrite on purpose
}
The regex isn’t decoration — it is the reason a hostile or broken client can’t put "abc" or "-5" into a money column.

Reading the money out of the payload is its own tested module

Turning { amount: "15173420", token: { decimals: 6 } } into 15.17342 is exactly the kind of small conversion that silently produces garbage — a missing decimals field would have divided by 10NaN and written "NaN" into your accounting. It now lives in lib/cctp/delivered-amount.ts with 8 tests, and its rule is:

Rule
If the payload is anything other than a clean whole number of wire units with sane decimals, return null — and null means keep the quoted figure. Never write a guess into a money column. A slightly pessimistic number is a much smaller problem than a nonsense one.

3 · The funding move sent more decimals than the swap could spend

When you fund a CCTP swap from Lobstr, the app moves USDC into your Normal wallet and then burns it. Those two steps disagreed about precision:

the move sent   amount.toFixed(7)   ← Stellar's precision (7 decimals)
the burn spends amount.toFixed(6)   ← CCTP's wire precision (6 decimals)

So the 7th decimal was carried across and then left behind, every time. Both are now 6 decimals: the amount moved is exactly the amount burned.

Honest sizing — this one is small
The stranded amount is at most 0.0000009 USDC per swap. That is a rounding artefact, not lost money, and I am not going to dress it up as a leak. It is worth fixing for a different reason: when the moved amount and the burned amount are the same number, the “did the funding land?” check is exact arithmetic instead of an approximate comparison — and that check is the one that, when it got the answer wrong, caused a real double-move.

4 · A fee of “NaN”

Two ends of the same problem.

The client’s guard didn’t catch it

const feeAmount = parseFloat(swapQuote.fee || '0');
if (feeAmount <= 0) throw new Error('Swap fee was not computed');

This looks airtight and isn’t. parseFloat("abc") is NaN, and in JavaScript every comparison with NaN is false — including NaN <= 0. So a non-numeric fee walked straight past the guard and became amount: "NaN" on the wire. The guard now asks Number.isFinite(feeAmount) first, which is the only reliable way to ask “is this actually a number?”

The server was quietly reporting a fee of nothing

The quote route sent the fee as String(quote.platformFee?.feeAmount ?? ''). If that field was missing the result was an empty string, the client read it as 0, and the swap was recorded as fee-free while Soroswap still took its cut — books that disagree with reality, with nothing in the logs. Now a single helper decides whether the figure is usable, and if it isn’t, the server refuses the single-signature path and returns 409 embedded_unavailable so the app falls back to the ordinary two-signature flow.

The pattern in all three fixes
When we can’t state a number truthfully, take a slower path that we can — never substitute a convenient zero. A wrong number is worse than a slow one, because a wrong number never announces itself.

5 · What I checked and deliberately did NOT change

Two items on the Wave 5 list turned out not to need code. Recording why, so nobody re-opens them:

flagged itemverdict
Inbound rows record dstAmount from the burned amount (state.ts) Not a bug — already the truth. We burn with CCTP_MAX_FEE = 0n and finality threshold 2000, i.e. Circle’s standard transfer, which mints 1:1. There is no slippage on that leg to under-report. Verified in lib/cctp/config.ts rather than assumed.
swap_logs.amountOut stores the quoted output, not the realized one Real gap, left open on purpose. Getting the true figure means parsing the Soroban call’s return value, which is shaped differently for each protocol (soroswap / phoenix / aqua / sdex). That is a genuine piece of work, not a one-liner — so the code now carries a comment saying plainly that the number is an estimate, and it is tracked for a later wave. The CCTP paths get real numbers because LI.FI reports them; the Stellar path doesn’t yet, and pretending otherwise would be the exact sin this wave is about.

6 · A test that lied about being green

The full run turned up one failure that had nothing to do with this wave — my own test for the request gate, from the honest-errors work:

expect(starts[2] - starts[1]).toBeGreaterThanOrEqual(20);
  Expected: >= 20    Received: 16

The gate was fine. The test measured the real wall clock, and on a loaded machine the operating system delivered a timer late. A test like that fails at random, and a suite that fails at random gets ignored — which is how a real failure eventually slips through.

The gate already accepts its clock and its sleep as parameters, precisely so this can be proven instead of timed. It now asserts the exact waits the gate hands out ([30, 60] — the first call isn’t held at all), with no reliance on real time.

A trap worth knowing
My first attempt at the fake clock advanced a shared counter inside sleep. That models something that never happens: three concurrent 30ms sleeps take 30ms in the real world, not 90. A fake clock that models the wrong physics is worse than a real one — it fails confidently. Ran it 5× to confirm it’s stable.

What “wrong” looks like here
This wave is about numbers in the database, so the failure mode is quiet. If an Activity row shows a delivered amount that is not a number (blank, NaN, 0) after a swap that clearly succeeded, that is a Wave 5 regression — send me the row and I will read it against the chain.
