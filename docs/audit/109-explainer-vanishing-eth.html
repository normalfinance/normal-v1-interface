The Vanishing ETH

Branch feat/swap-matrix-hardening, run 14 — ETH correct, then 0 for a few seconds, then correct again. Diagnosed and closed.

1 · What you saw, decoded

This is a different bug from yesterday’s races — a zero is not a stale value, it is a wrong answer. Here is the chain, each link verified in code:

stepwhat happened
1Your swap delivered; a good refresh showed ETH correctly. ✓
2~10s later another refresh ran (the post-delivery burst). In that one run, the ETH balance read failed — one provider hiccup on one request. The aggregate marks that honestly as balance: null, status: 'error'.
3The server has a safety net for exactly this — it backfills an errored row from its last-good snapshot in Redis. That backfill missed (a Redis read blip, or nothing usable) — so the null reached your browser.
4The display layer turned the honest null into a lie. The token mappers coerce null → '0', and the drawer filters rows with balance > 0 — so ETH did not show as 0.00, it vanished from the list entirely, which reads exactly as “went to 0”.
5The next refresh read ETH fine and the row came back. ✓

I also verified what it was not: your ETH RPC is keyed Alchemy and answered 8 rapid probes consistently; the server’s rpc() helper correctly rejects error responses rather than turning them into zeros; and the no-clobber rule from yesterday cannot create this (it only rejects older payloads — the errored one was newer).

Was it something I plugged in?
Not directly — every link in that chain predates this week. But indirectly, yes, in one honest sense: the refresh machinery now runs more reads around a swap than before, and more reads means more chances for one to hiccup and expose this display hole. The hole was always there; the traffic that found it is newer.

2 · The fix: a known number never becomes a hole

One new pure rule, beside yesterday’s no-clobber rule and composed with it at every place a payload lands:

fillErroredFromKnown(incoming, known):
  a row arriving with balance = null (source FAILED)
  while we already hold a real number for that asset
  → keep the known number, marked 'stale'
  a row arriving with balance = '0' (a REAL zero — emptied wallet)
  → passes through untouched

So a failed read now degrades to “your last known balance, marked stale” instead of a vanished asset. The distinction that makes this safe is the same one running through this whole project: null means the question failed, '0' means the ledger answered zero — and only the second is allowed to look like a zero.

Matching is by chain and symbol together, so a Stellar USDC value can never patch an Ethereum hole. 5 new tests, including the live case and the real-zero passthrough.

And the silence is fixed too

Nothing anywhere logged which source failed — step 2 was invisible. The aggregate now names it:

[portfolio] eth source failed: <reason>

If you ever see a balance misbehave again, the dev-server terminal will say which provider hiccuped, when.

3 · Why not fix the mappers or the drawer filter instead?

Because they are many and this is one. The null → '0' coercion exists in several mappers, and the > 0 filters exist in the drawer, holdings and hero views — patching each would be five fixes that must never drift. Patching the data once, where it lands, fixes every surface at the same time. (The deeper cleanup — surfaces rendering status: 'stale' visibly, doc 90’s deferred visuals — stays on that list; this change makes the data they all read truthful.)
