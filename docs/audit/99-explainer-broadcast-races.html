One Transfer, One Share

Branch feat/swap-matrix-hardening, run 4 (2026-08-27) — doc 95 Wave 3: races where two things happen at once and money gets attributed to the wrong one.

1 · The headline bug — found in your own account

What happened

Two BTC→USDC swaps were started 30 minutes apart. Both bridges delivered USDC to the same Base address, because that address is your wallet. Then:

row A (20:53)  quoted 15.45 USDC   →  its USDC arrived on Base
row B (21:24)  quoted 15.17 USDC   →  its burn ran and took 15.59  ← row A's money
row C (21:35)  quoted 16.75 USDC   →  its burn took 32.40           ← ~2 transfers' worth

Row A never burned anything and sits in CREATED to this day — permanently stuck, because the money it was waiting for had already been carried away under a different row's name.

Important: no money was lost
Every dollar reached your Stellar wallet — it was all your own money going to your own account. What broke was attribution: one transfer can never complete, and the Activity feed reports the wrong amounts (a row quoting 16.75 showing 32.40).

Why it happened

The burn and pivot steps both asked "how much USDC is at this address?" and moved all of it. That's correct when one swap is in flight and wrong the moment two are. Meanwhile the browser-side code had the opposite bug: it clamped to the quoted minimum exactly, so when a route delivered slightly more than quoted, the extra was stranded on Base forever.

The fix — one rule, shared by every leg

A new pure function decides how much a transfer may move:

take = min(what's actually there, what this row quoted + 5% slippage headroom)
  • One swap in flight → it takes everything including positive slippage (fixes the stranding).
  • Two swaps in flight → each takes only its own share (fixes the sweeping).
  • Partial arrival → takes what's there.
  • A refund row carries no quote → sweeps everything, as refunds must.

Used now by all four places that move USDC on Base: the server burn, the server pivot, the browser's inbound leg, and the recovery banner. Pinned by 7 tests built from your real numbers, so the two opposite mistakes can't come back.

2 · A broadcast that succeeded must never be forgotten

The server signers used to: broadcast → wait for the receipt → then record the hash. If the wait failed (an RPC hiccup, or the serverless function hitting its time limit), a real on-chain transaction was thrown away — and the app then signed a second burn. Now the hash is written to the row the instant it is broadcast, before any waiting.

3 · Nonce races — the gap I had left open

Yesterday I fixed "nonce too low" in the browser signers. I did not port that fix to the server ones, so an autopilot leg still died if your tab broadcast something at the same moment. Fixed in both server signers — and because the autopilot signs without prompting you, those retries cost nothing.

The same guard now covers the LI.FI Ethereum leg: its nonce is read, then gas checks and a 10–30 second passkey happen, and anything else your wallet sends in that window claims the nonce first. It rebuilds and re-signs once (that one does cost a second prompt — unavoidable, since the signature covers the nonce).

4 · Bitcoin: don't report failure for a transaction that's live

If the broadcast request timed out or the response was lost, we reported failure — while the transaction was sitting in the mempool. The user would then re-sign, risking a double spend of the same coins. Now the transaction ID is computed locally before broadcasting, so on any failure we simply ask the network "is this already there?" and report success if it is.

5 · The double-funding cluster (the 2026-08-22 incident's leftovers)

When you fund a swap from Lobstr, a guard records "I already moved 100 USDC for this swap" so a retry can't move it twice. Two holes remained:

holeconsequencefix
The guard was cleared by any swap finishing, on any engine Fund from Lobstr → CCTP swap fails → do an unrelated Stellar swap → retry → money moves a second time The guard now clears only when the amount itself changes — the real "different swap" signal

6 · Stellar relayer sequence collisions

Two different transfers minting at the same moment share one relayer key, and the loser fails with a sequence error. The row itself was already protected from double-minting, so the only thing missing was a retry: it now rebuilds with a fresh sequence and tries up to three times.

7 · How to test

You do NOT need the cron for this — on localhost or anywhere
Leave the /swap page open. The recovery banner above the swap card refreshes every 30 seconds and pokes each in-flight transfer, which advances it server-side (attestation → mint). That is what carries a bridge forward while the popup is closed. The cron is the safety net for when nobody has the app open at all.

Test A — the headline: two swaps must not eat each other (QA R47)

Any pair of swaps that puts USDC on your Base address twice will do. Two variants:

#doexpect
1 Outbound variant. Swap 15 USDC → ETH. After signing, close the popup. Leave the /swap page open and watch the banner appear — it advances the bridge on its own (~1–2 min to mint). Then swap 15 USDC → BTC and let that one finish in the popup. Finally click Finish transfer on the ETH row in the banner. The BTC swap delivers about $15 of BTC — not ~$30. Then the ETH row's Finish still works and delivers ETH.

The old bug's fingerprint: the BTC swap delivering roughly double, and Finish on the ETH row then failing with "No USDC found on Base" — because its money had been swallowed.
2 Inbound variant (closer to the original incident, no Finish click needed): start BTC → USDC, then a few minutes later ETH → USDC, so both bridges deliver USDC to Base around the same time. Both complete. Neither is left stuck in CREATED with nothing to burn.

Expect amounts to be approximate. The row that goes second takes its own share plus 5% slippage headroom, so the first one delivers slightly under its quote (e.g. ~14.25 instead of ~15). Nothing is lost and nothing is orphaned — that is the trade-off on purpose.

Test B — the funding guard (QA R48)

Fund a CCTP swap from Lobstr, let it fail, then run any unrelated swap (a Stellar USDC↔XLM one is quickest), then retry the first swap. The USDC must not leave Lobstr a second time.

Test C — slippage and nonces (QA R49)

On any completed swap, compare the delivered amount to the quote: it should be a little above the quoted minimum, not exactly equal (positive slippage is now bridged instead of stranded on Base). In the server logs during an autopilot leg there should be no "nonce too low" failure — a race shows up as a silent rebuild.

If something looks wrong

The database is the source of truth: send the transfer rows and I will read the on-chain reality against them, the way the original bug was found.
