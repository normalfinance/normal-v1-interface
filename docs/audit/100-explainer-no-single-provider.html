No Single Point of Failure

Branch feat/swap-matrix-hardening, run 5 (2026-08-27) — doc 95 Wave 4: every money path now has a second way through.

1 · The idea

To move money on a blockchain you have to talk to a node — someone else's server. If the one node you use is slow, rate-limited, or down, your transaction doesn't fail cleanly; it fails in whatever way that node happens to break, sometimes after the user has already signed. Wave 4's rule: no leg that moves money may depend on one provider.

The gap this closes
Wave 1 of the honest-errors work gave the browser fallback lists. The server never got them — so the autopilot burn, the autopilot pivot, the balance reads that decide how much to move, and the relayer's mints all ran through a single unkeyed public endpoint. That's the half of the system that runs when the user isn't watching.

Order matters

Keyed endpoints (paid, higher rate limits) are tried first; public ones are the safety net. The server-only keys never reach the browser — in client code those variables read as undefined and simply drop out of the list.

Why Bitcoin needed a second relay specifically

A signed Bitcoin transaction is worthless until someone accepts it. With one relay, a rate-limit window stranded a transaction the user had already approved with their passkey, and they had to re-sign against a quote whose deposit channel might have expired. Blockstream is an independent operator serving the same purpose — combined with last run's idempotency fix (the transaction ID is computed locally), a broadcast now has two ways to land and a reliable way to tell whether it already did.

Why the Horizon retry matters more than it looks

That read answers "did the USDC actually arrive in the Normal wallet?" after a Lobstr funding move. A rate-limit blip made it answer no about a move that had genuinely happened — and the user's retry moved the money a second time. It's the same failure the Wave 3 guard protects against, one layer down: an unreliable answer treated as fact.

3 · How to test

This wave is invisible when everything works — which is the point. The honest test is that nothing changes:

#doexpect
1Run one swap of each kind you normally test (Stellar, CCTP in, CCTP out, a BTC one) Everything behaves exactly as before. No new prompts, no new errors — the fallbacks are only consulted when the first provider fails
2Optional, in devtools: block mainnet.base.org and run a CCTP swap The swap still completes through the next endpoint in the list, instead of failing
3Optional: block mempool.space and send BTC The broadcast goes out via Blockstream; the server log names which relay was used
Verified structurally
A repository-wide search confirms there is no longer a single transport: http() (viem's unkeyed default) anywhere under server/, lib/ or the API routes — every money path is pooled.

4 · Deliberately still open

The wallet-setup dialog's funding step still decides "ready" from an absolute balance, so a companion that already holds enough USDC can skip the "move your USDC" step — the second entry point of the double-funding problem. It is not being patched here on purpose: the run-page work (doc 93 phase 0c) folds wallet setup into the swap's own step list, which removes the second path entirely rather than adding a second guard to it.
