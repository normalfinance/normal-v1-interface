2 · 68 variables the build cache could not see

Turborepo decides "did anything change since the last build?" by hashing the inputs it has been told about, in turbo.jsonc. A variable the app reads but the config never mentions is invisible to that hash.

change NEXT_PUBLIC_TURNKEY_RP_ID  →  rebuild  →  turbo reports a CACHE HIT
                                  →  the previous bundle ships, still carrying the old value

Nothing in the diff explains it. It bites hardest on NEXT_PUBLIC_*, which Next.js inlines directly into the JavaScript at build time — the value is baked into the file, so a stale bundle is a stale value, not just stale code.

The count:

Count
Variables the app reads (process.env.X)96
Declared in turbo.jsonc56
Read but undeclared68

(68 exceeds 96 − 56 because some declared entries were themselves unused.)

And the undeclared list was precisely the set whose silent staleness is hardest to diagnose:

NEXT_PUBLIC_TURNKEY_RP_ID          ← the passkey domain
NEXT_PUBLIC_SUPABASE_URL / ANON_KEY
NEXT_PUBLIC_MAINNET_USDC_ADDRESS / XLM_ADDRESS / DEFINDEX_VAULT
NEXT_PUBLIC_AUTOPILOT_PUBLIC_KEY
TURNKEY_* · AUTOPILOT_* · CCTP_* · LIFI_* · SOROSWAP_* · CRON_SECRET
SUPABASE_SERVICE_ROLE_KEY · HELIUS / ETHERSCAN / COINGECKO / DUNE keys
Why this one was worth doing first
We had just spent a day on a passkey failure where the config said one thing and the deployed bundle behaved as though it said another. This is the mechanism that produces that class of bug on purpose. Fixing it first means every later deploy on this branch is trustworthy.

Also removed: MNEMONIC_ENCRYPTION_SECRET, declared but read nowhere in the source. Two more dead secrets live in .env only — see §9.

A correction on the record

The first version of this analysis reported "zero declarations". That was task-level env; globalEnv existed with 56 entries. The real figure is the 68 above.

3 · The guard is a test, not a script

Adding 68 names fixes today. It does nothing about the next variable someone adds. The plan called for a CI script — but the repo already runs Jest in CI, and Jest can read files, so the guard became a test instead: no new dependency, no new pipeline step, and it fails on the pull request that introduces the gap.

src/utils/turbo-env-audit.ts        pure helpers
src/utils/turbo-env-audit.test.ts   4 unit tests + 1 whole-tree guard

The helpers are pure and tested separately on purpose. A guard that silently passes — because its own parsing is broken — is worse than no guard at all, since it also removes the suspicion that something might be wrong.

4 · An open door into the database

GET /api/wallet/activity took a wallet address in the query string and returned that address's confirmed savings deposits and swaps. No login. No rate limit.

The register dismissed it as "chain data is public anyway". That is true of the content — every row carries a transaction hash and the same facts sit on the Stellar ledger. It is not true of what we were doing:

  • we served a curated, filtered, ready-to-parse index of someone's money movements, where the ledger requires scraping and reassembly
  • every call was two unauthenticated Postgres queries — an open load channel into the database, not just a privacy question

Decision A was taken: the route now requires a session and checks ownership, exactly like the two log-transaction routes. userOwnsWallet consults both turnkey_wallets and linked_wallets, so a hybrid user's companion wallet and their connected Lobstr wallet both still pass.

Why private, when the data is public anyway
Going private → public later is an endpoint you design, cache and rate-limit deliberately. Going public → private later means breaking whatever grew to depend on it. "Public by design" is a choice; "public by accident" is what this was.

5 · Two near-misses the change almost caused

Wrapping a route in authentication is a two-line change that can break a feature in two directions. Both happened here, and both were caught before merge.

The caller had no session

fetchWalletActivity used a bare fetch(url). Adding withAuth without touching it would have returned 401 to every activity feed.

Why that would have been nasty
The fetcher returns [] when the response is not a success. So the failure would have rendered as an empty activity list — indistinguishable from "this wallet has no activity yet". A silent, plausible-looking wrong answer beats a loud error at hiding from you.

The conformance guard still blessed the route

route-auth-conformance.test.ts exists so no route is born public by accident: every route must use withAuth or appear in an allowlist with a reason. wallet/activity was in that list as "scoping decision pending". Left there, the guard designed to prevent this exact class of problem would have kept approving it. The entry is removed, with a note that it must never return.

6 · The limit that never reached Postgres

Found while reading the route for the auth change, unrelated to it:

const limit = parseLimit(...)                      // parsed
prisma.vaultDeposit.findMany({ where, orderBy })   // no `take`
prisma.swapLog.findMany({ where, orderBy })        // no `take`
items.slice(0, limit)                              // trimmed only here

Cause and effect: a wallet with 5,000 confirmed rows and a request for 50 → Postgres reads and ships all 5,000, and 4,950 are thrown away in the Node process. Your heaviest users generate your heaviest queries, on an endpoint the drawer opens on every visit. Both queries now carry take: limit.

7 · #40: one row, two seeds, wrong phrase

The register said: "Importing a Normal Stellar wallet hides the Turnkey one. VERIFIED cosmetic (DB keeps both). Fix = wallet list."

It cannot be. turnkey_wallets.supabaseUid is unique, so there is exactly one row per user and the database cannot keep both. Reading the import path:

  • /api/turnkey/import always overwrites walletId with the imported wallet — it even logs Replacing existing wallet reference
  • address columns are additive: if (addr && !row[col]), so an already-populated stellarAddress is left untouched
  • importMnemonicIntoTurnkey explicitly supports an existing sub-org (it skips the passkey ceremony when one exists), so this path is reachable by design, not an edge case

So a user who creates a Normal wallet and later imports a mnemonic ends with one row describing two seeds:

row.walletId        →  wallet B  (the imported one)
row.stellarAddress  →  wallet A  (the original, never overwritten)
Why this is not cosmetic
wallet-export-dialog exports wallet.walletId. So "Export recovery phrase" hands the user wallet B's phrase, while the app shows and spends wallet A's Stellar address. They save a phrase that does not control the balance they are looking at. Separately, addWalletAccounts derives new chains from walletId, so a later "Set up BTC wallet" lands on B while Stellar stays on A.

The existing stellarMatch guard does not catch this: it compares the derived address against the mnemonic's own expected address, never against the row's pre-existing one.

Confidence, stated honestly
This is read from code, not reproduced live. It is written up rather than fixed because the right fix is a product decision — refuse the import, migrate the row wholesale, or model multiple wallets per user — and each implies different UI and different migration work. Building a "wallet list" on top of the current row would have hidden the real defect behind a nicer display.

9.2 #40 — the wrong-phrase defect (highest severity of the three)

Step one is a live reproduction, because everything below rests on code reading alone. On staging: create a Normal wallet, note its Stellar address, then import a different mnemonic into the same account. Then compare four things:

row.walletId          vs  the imported wallet's id
row.stellarAddress    vs  the address the app displays
Turnkey getWallets    →  does the sub-org now hold two wallets?
Export recovery phrase →  which wallet's phrase comes back?

If it reproduces, three fixes are possible and they are genuinely different products:

OptionWhat the user experiencesCost / risk
A. Refuse the import when the account already has a wallet "You already have a Normal wallet. Importing another is not supported yet." Smallest, safest, ships today. Removes a flow that currently appears to work — and that some users may have already used, so it does not repair existing rows
B. Migrate the row wholesale — import replaces every address, not just empty columns The imported wallet fully becomes their Normal wallet; the old one is abandoned Honest and consistent, but silently strands any balance on the original wallet unless we check balances first and refuse or warn
C. Model multiple wallets per user Both wallets visible, switchable, each with its own phrase — this is also the real fix for the drawer list that #40 was originally filed about Largest: schema change, migration, UI, and every place assuming one wallet per user
Recommendation
A now, C later. A closes the dangerous state in an afternoon and buys time; C is the honest end state but should not be rushed under the pressure of an active defect. B is the one to avoid — "helpfully" overwriting the record of a wallet that may hold funds is how a cosmetic bug becomes a loss. Whichever is chosen, add a repair pass for any row where stellarAddress does not belong to walletId.

9.3 feat/autopilot-monitoring — the gap we chose

Removing the $2k / $10k caps (doc 76 §4 reversal) traded prevention for detection. The detection does not exist yet, which makes this the largest known gap in the system today.

PieceSketch
Key rotation AUTOPILOT_API_PRIVATE_KEY is the only key that can move user funds. Rotation means adding a new API key to the delegated user, switching the env, then deleting the old one — the Turnkey policy keys on the user id, not the key, so the policy survives rotation untouched. Needs a written runbook more than it needs code
Alerting autopilot_signatures already records every attempt with an outcome and a USD amount. Two alerts pay for themselves: a single leg above a threshold you choose, and a spike in refused-* rows (which is what a key being probed looks like). The cron heartbeat is the natural place to evaluate them
Kill-switch drill AUTOPILOT_DISABLED=1 plus a deploy stops all autopilot signing. Worth testing once, deliberately, and making sure someone other than you can do it

9.4 Phase 5 — load tests and monitoring

The last phase of the optimisation project, never started. Everything this project claims about capacity — the 15-second shared balance cache, the one-hour last-good snapshot, the single vault-info entry serving every user, halving request volume by removing the redirect hop — is reasoned from the code and never measured under load.

Scope, per the earlier no-staging-database decision: read-path load tests against the cached endpoints, plus monitoring and alerting including cron heartbeats. The point is not to discover that the caching works; it is to find the first thing that breaks at 10k and fix it while it is cheap.

Honest framing
The building is done and the proving is not. Of the remaining work this is the only item where being wrong is expensive, because you would find out from users rather than from a test.
The recurring shape, one more time
Three of this week's bugs — the orphaned passkey, the chain account Turnkey already had, and the autopilot grant that arrived mid-swap — share one root: the expensive step succeeded, the record did not, and the retry repeated the step instead of adopting what already existed. #40 is the same shape with the roles swapped: the record was overwritten while the thing it described stayed put. When you touch a flow that writes a record after doing real work, ask what a retry sees, and what the record now claims about reality.
