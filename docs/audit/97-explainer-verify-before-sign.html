Verify Before You Sign

Branch feat/swap-matrix-hardening, run 2 (2026-08-27) — doc 95 Wave 2. Five places where we broadcast or signed something nobody had checked.

1 · The idea in one sentence

A signature is a promise you can't take back. Every place in the app where the user (or our server) signs or broadcasts something built by someone else — Soroswap's transaction, LI.FI's Bitcoin PSBT, Circle's attestation message — we were taking it on trust. Wave 2 checks each one against what we asked for, and refuses when it doesn't match.

2 · What changed, one by one

2.1 The single-signature swap route was missing its guards

/api/swap/submit-single broadcasts a signed Stellar transaction and writes a money row. It did require login — but unlike its sibling execute-pair, it never checked that the wallet inside the transaction actually belongs to the caller, had no rate limit, and used a hardcoded Horizon URL instead of the network config.

  • Now: rate-limited; the transaction's source must be a wallet you own (403 otherwise); Horizon/passphrase come from the shared config like everywhere else.
  • Now: it verifies our 0.5% fee is genuinely inside the transaction before broadcasting — this route exists only for the embedded-fee flow, and nothing checked the fee was there.
Verified, not assumed
Before writing that fee check I called Soroswap's live build API and inspected the bytes it returns: the fee address is embedded as its raw 32-byte key (platformFee: {feeBps: 50, feeAmount: "50000"}). That's why the check can be enforced immediately instead of shipped in "log only" mode.

2.2 The aggregator's transaction is checked before you're asked to sign it

Soroswap builds the swap transaction; we passed it straight to your wallet. Now, before it ever reaches you, we verify (a) the transaction spends your account — not someone else's — and (b) when we asked for the embedded fee, the fee address is actually in it. If either fails, the app falls back to the standard two-signature flow instead of signing something unverified.

2.3 The Bitcoin PSBT is inspected before the passkey prompt

This is the highest-stakes one. A PSBT is a pre-built Bitcoin transaction: whoever builds it decides where your coins go. We signed LI.FI's without looking at the outputs. Now, before signing, we refuse if:

checkwhat it prevents
exactly one real payment output (ignoring the OP_RETURN memo)change or a slice being routed to an address that isn't the bridge or you
that output pays at least the quoted amountdepositing less than the swap you agreed to
miner fee ≤ 25% of the amount (when all inputs are yours)a malformed route burning most of your BTC as fee
an input that's ours but unsignable → error, not skippeda half-signed transaction that dies at broadcast after your passkey
honour the input's declared signature typea signature that looks valid locally and is rejected by the network — "sent but never arrived"

Unchanged on purpose We still never modify the PSBT — altering a Chainflip deposit can make it unrefundable. We only refuse to sign it.

2.4 Circle's message must belong to your transfer

To finish a bridge we fetch the "attestation" for your burn transaction and mint with it. We used to take the first message in Circle's reply. A transaction can carry more than one CCTP message — minting the wrong one would strand the other. Now we decode each message's own header (source and destination domains) and use only the one matching your transfer; if none matches, we mint nothing and log it. Covered by 6 new tests.

2.5 Refunds must name the swap they're recovering

The refund path bypasses the $10 minimum and the emergency cap — correctly, since it recovers money that already moved. But refund: true came from the request body with nothing behind it, so a crafted request could open unlimited tiny transfers that our relayer pays gas for. Now a refund must reference one of your own unfinished outbound swaps, verified server-side. Also fixed: a non-numeric emergency cap silently disabled the cap — it now logs loudly instead.

3 · How to test

#doexpect
1Run a normal XLM↔USDC swap (single-signature path) Works exactly as before — the new checks pass silently. If the console/server log shows "fee address absent", tell me: that means Soroswap changed their encoding and the app correctly fell back to the two-signature flow
2Run a BTC-source swap (e.g. BTC→USDC) Passkey prompt appears and the swap proceeds as before; the PSBT checks run silently ahead of it. Any refusal message starts with "Refusing to sign:" and says exactly why
3Trigger a refund via "Bring back as USDC" Works as before (the client now sends the original swap's id). A refund request without a valid original swap is rejected with "Refunds must reference one of your unfinished swaps"
4Complete any CCTP bridge end-to-end Mint still happens normally; server logs show no "none targets domain" warnings
