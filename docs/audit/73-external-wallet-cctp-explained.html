External Wallets × Cross-Chain Swaps

Everything built on branch feat/external-wallet-cctp — explained for the whole team, with the full test plan. Design docs: 72 (architecture) · 73 (this explainer, markdown twin) · Register entries: #32 chunks 1–4e.
The goal in one sentence
A user whose Stellar wallet is Lobstr, Freighter, Ledger or WalletConnect can now swap USDC into BTC / ETH / SOL and back — which physically requires our passkey-secured Normal wallet (external Stellar wallets cannot sign on other chains) — without ever losing sight of their own wallet, with as few signatures as possible, and with nothing ever happening silently.

1 · Background: why this was hard

The app was built around one “connected wallet” slot — like a TV with a single HDMI input. Balances, savings, sends, swaps: every screen read from whatever was plugged into that slot. That was fine when every user had exactly one wallet. But cross-chain swaps need the Normal (Turnkey passkey) wallet — the only wallet that can sign on Bitcoin, Ethereum, Base and Solana — so an external-wallet user needs two wallets coexisting: their own external Stellar wallet plus a Normal wallet for everything non-Stellar.

Two locked product decisions shaped the whole build:

  • Transfer-first: the external wallet never signs non-Stellar legs. To swap funds held externally, they hop to the Normal wallet first (one visible approval) — and every future swap is then passkey-only, which is the path to the one-signature goal (#33).
  • No picker, no hiding: everything the account owns is displayed, every number is labeled with the wallet that owns it, and the wallet that signs is decided by where the action starts — never by a modal asking the user to choose their identity.

2 · Chunk 1 — stop silent wallet switching (invisible, foundational)

The problem. Two pieces of background code shoved a different wallet into the slot uninvited:

  1. Wallet creation stole the screen. Creating a Normal wallet while Lobstr was connected replaced Lobstr in the entire app mid-flow — balances, savings, activity all flipped.
  2. The “self-heal” hijacked an empty slot. Whenever the slot was empty, a recovery routine plugged the Turnkey wallet in. Great on a new laptop (your wallet just appears); terrible after you deliberately disconnected an external wallet — reload, and you were silently in a different wallet (long-standing bug #42).

The fix. A persisted breadcrumb — lastWalletType — records the wallet you last chose to connect and survives disconnect. An empty slot now has two distinguishable meanings:

  • breadcrumb absent → fresh device / cleared storage → restore the Turnkey wallet (new-laptop login unchanged);
  • breadcrumb says “lobstr” → the user disconnected on purpose → stay disconnected.

Wallet creation now adopts the new wallet into the slot only when the slot is empty (signup — unchanged). With an external wallet connected, the new Normal wallet is linked to the account and the screen doesn't blink. All of it is pinned by named invariant tests (I1 “creation never steals”, I2/I7 “external disconnect stays disconnected”, I5 “signup still adopts”, I6 “new-device login still restores”) — if a future change breaks a promise, a test with that name fails.

3 · Chunk 2 — show everything the account owns, split by wallet

  • Server: the portfolio endpoint returns a companionStellar field — the Normal wallet's XLM/USDC — whenever the connected wallet is external. Cost: exactly one extra Horizon call riding the existing 15-second cache. Single-wallet users: zero change.
  • Drawer: with two wallets, the Assets tab shows Normal wallet Lobstr tabs — each wallet's own token list under its own shortened address. Numbers are never summed across wallets in lists (a sum no single action can spend is a lie); the Total-balance row does sum the account, because a total is information, not an action.
  • Portfolio & home pages are the account-wide wealth views: the Normal wallet's assets stay visible when an external wallet connects, as rows labeled “· Normal wallet”, and on hybrid accounts every row is labeled by its owning wallet.
  • Savings display is account-wide too — your position shows no matter which wallet is connected — while deposit/withdraw math stays strictly per-wallet (limits and commissions can never mix wallets). A banner on the savings card tells a hybrid user where their savings actually live.
  • The unlink guard: the settings page used to happily offer “Disconnect” on the Turnkey wallet — the wallet holding all the user's funds. The server now refuses (400) and the settings card explains instead. Two layers on purpose: a UI bug can't reopen the hole.
  • Why no database change? The tables already supported coexistence: turnkey_wallets = one Normal wallet per account; linked_wallets = many external wallets per account. Only the browser's “who signs right now” slot is single — necessarily, since an external wallet signs only while its app session is open.

4 · Chunk 3 — the guided “get a Normal wallet” popup

Who sees it
Only an external-wallet user who starts a cross-chain swap without a Normal wallet. Signup/onboarding is untouched — same asset-first flow as before, pinned by test I5. Normal-wallet users never see this dialog.

The dead “cross-chain needs your Normal wallet” button became “Continue with your Normal wallet”, opening a four-step dialog. Each step happens at the moment it's physically required:

StepWhat happensWho signs
1 · CreatePasskey ceremony creates the Normal wallet. Chunk 1's guard keeps the external wallet connected — the screen doesn't blink.passkey
2 · ActivateA new Stellar account doesn't exist until it receives XLM (Stellar's rule). Pre-filled 4 XLM payment from the external wallet — enough to land the new wallet “green” on the fee semaphore from day one.external wallet
3 · TrustlineStellar wallets opt in to each asset; one tap adds the USDC line. Signed by the passkey automatically, because the transaction's source is the Normal wallet — the universal signer routes by source account.passkey
4 · FundPre-filled USDC transfer (the typed swap amount) from the external wallet.external wallet

Resumable by construction: the current step is derived from chain state on every open — “does the wallet exist? is it funded? has the trustline? enough USDC?” — never remembered. Kill the tab anywhere; reopening resumes exactly there. A returning user with a funded wallet skips the dialog entirely. One-time cost: 2 passkey ceremonies + 2 external approvals. After that, every swap is passkey-only.

Also in this chunk: the drawer's “+” button becomes “Connect external wallet” for anyone who already has a Normal wallet (opens the wallet picker directly), and the ⟳ button was renamed “All wallets”.

5 · Chunk 4 — the swaps themselves

The design covers every place funds can sit (doc 72 §4h). N = Normal wallet, E = connected external wallet:

ScenarioHow it runsApprovals
USDC on N → BTC/ETH/SOLplain swap, Stellar side pinned to the Normal walletpasskey only
USDC on E → BTC/ETH/SOLmove-and-swap: one pre-filled transfer E→N, then the swap1 external + passkey
BTC/ETH/SOL → USDCplain swap; the user picks the landing walletpasskey only
BTC ↔ ETH ↔ SOLpure Turnkey-chain swap, no Stellar at all — simply un-gatedpasskey only
XLM → cross-chainunchanged: swap XLM→USDC first (Soroswap, the connected wallet)—

The source picker (outbound)

On USDC → BTC/ETH/SOL, a hybrid user sees two pills above the amount — Normal wallet · 27.48 Lobstr · 12.50 — and balance, validation and MAX all follow the selected pill. Picking the external wallet changes the button itself to “Move 12.50 USDC from Lobstr & swap” with a helper explaining both halves; the progress popup shows “Moving USDC from Lobstr” as its own step, and the move is a normally recorded transfer in Activity.

The safety rule that makes move-and-swap sound
The engine does not touch the bridge until the moved USDC is visible on the Normal wallet — it re-reads the balance in a bounded loop before proceeding (verify-before-act, the #62 rule). A transfer that lags can only make the swap wait, never burn money that hasn't arrived. If the move fails or is declined, the message says plainly: “nothing was swapped”.

The delivery picker (inbound)

On BTC/ETH/SOL → USDC, a “Deliver to: Normal wallet / Lobstr” row picks where the USDC lands (default: Normal wallet). External delivery needs that wallet's USDC trustline — if missing, the pill reads “Lobstr · add trustline” and tapping it runs the opt-in signed by the external wallet itself. No dead ends.

The preflight ladder

The swap button never dead-ends; it always names the next step and opens the right dialog for it:

  • no Normal wallet → Continue with your Normal wallet (guided setup)
  • missing USDC trustline → Add USDC to your Normal wallet (setup resumes at that step)
  • fee-XLM dry → Top up XLM to swap (the burn pays its Stellar fee in XLM from the Normal wallet — a wallet the user may never have topped up; the setup's XLM step doubles as the top-up)
  • everything ready → Swap (or Move X & swap)

6 · Bonus fix — sending to a brand-new wallet

Testing surfaced a hole that predates this project. Stellar has two rules our send flow ignored: an address that never received XLM does not exist on-chain (the first XLM must arrive via a special createAccount operation of at least 1 XLM), and a wallet can hold USDC only after opting in with a trustline — which only that wallet's own key can add.

Every send used to be a plain payment, so both cases failed on-chain, after signing, fee burned, with a raw error code (op_no_destination / op_no_trust) as the only explanation. Now, in the one shared send funnel (send modal, guided setup and move-and-swap all inherit it):

  • XLM to a fresh address → automatically switches to the activation operation (below 1 XLM: a clear message about the minimum);
  • USDC to a fresh address → blocked before signing: “send at least 1 XLM first, add a USDC trustline there, then send USDC”;
  • USDC to an active wallet without the trustline → blocked before signing, telling the user to add the asset in that wallet's app;
  • if the trustline state can't be determined, the send is not blocked — the chain stays the judge, we never block on a guess.

7 · The safety rules behind everything

  • No silent wallet switching. The slot changes only by explicit user choice; every automatic writer is guarded and test-pinned.
  • No silent money movement. Every transfer is announced in the button label before signing, shown as a step in the progress popup, and recorded in Activity.
  • Every number is owned. On hybrid accounts, every balance on screen is labeled with the wallet that can actually spend it; lists never sum across wallets.
  • Account view vs wallet view is always an explicit choice. Pages show the account; action surfaces show one wallet. Defaulting to “whatever is connected” is how assets appear to vanish — that lesson cost us three field fixes in one day.
  • Verify before act. A burn never fires until moved funds are visible; “Done” never shows until the wallet displays the result.
  • Block before signing, never after. Preflights (trustlines, activation, fee XLM) run before any signature, so a fee is never burned on a doomed transaction.
  • Funds sit on the user's own addresses at every step — both wallets are theirs; the app never custodies anything in between.

8 · What deliberately did NOT change

  • Signup and login. Asset-first onboarding is byte-identical; a recognized returning user still lands straight in the app (test I8). New-device login still restores the Normal wallet (test I6).
  • Single-wallet users — today's entire user base — see zero visual difference anywhere: no pills, no labels, no tabs.
  • Savings actions stay scoped to the connected wallet; XLM ↔ USDC swaps still run on whichever wallet is connected.
  • The database schema. No migration was needed — the tables already modeled coexistence.

9b · Added after the matrix was written (2026-08-17)

Everything below landed on this same branch after live testing began. Junior summary per feature, then the extra test rows.

Stellar swaps from either wallet (chunk 4f)

XLM↔USDC swaps got the same wallet pills as cross-chain: pick Normal wallet → passkey signs both transactions, pick Lobstr → the kit signs, and balance/MAX/validation follow the picked wallet. The card opens on whichever wallet can actually pay. (Rows B6/B7 above.)

USDC-readiness notices (#74)

A wallet without a USDC trustline BOUNCES incoming USDC back to the sender. One shared probe now drives every notice: swap-page banners, a warning next to the receive QR, a badge inside each drawer wallet tab, and a one-time toast after connecting an external wallet. A FAILED probe shows nothing — the app never claims "not activated" off a network blip. The Set up button opens a guided popup: QR to fund with XLM (auto-advances when the payment lands — no button to press), then a kit-signed trustline.

Send: own wallets as first-class citizens (#74b/c)

"Your wallets" chips fill the destination (companion + ALL linked wallets, readiness-aware: unactivated targets stay selectable for XLM — that send activates them — but are disabled with the reason for USDC). And the companion Normal wallet's XLM/USDC are now sendable while an external wallet is connected — rows named "· Normal wallet", passkey signs, MAX/reserve/savings-buffer follow the owning wallet. The self-send guard now compares against the wallet the send RUNS FROM, so Normal→Lobstr works.

One data source everywhere (#75)

Root cause of "surfaces disagree": a legacy client-side token store that only refreshed on certain mounts, next to the server portfolio aggregate that refreshes after every transaction. Send, drawer and the fee card now read the aggregate; a layout listener keeps the store fresh for the one remaining consumer (swap card, Phase 2). Also composed for hybrid: the Earnings stat (slot + companion), the savings chart/history (follow the wallet HOLDING the savings), Holdings wallet tabs on /portfolio, per-wallet XLM fee rows ("2.00 XLM · 0.50 for fees") with a worst-wallet header chip, and the drawer address list collapsed to "Addresses · N".

Part F — the final polish round (2026-08-18)

What changed, in plain words: the Activity feed used to show only the connected wallet's history — your Normal-wallet deposits and swaps were invisible while Lobstr was connected; now both feeds are merged and every row says whose it was. The swap card was the last screen reading the OLD balance list (the one that only refreshed on page load) — it now reads the same live source as everything else, and its asset picker shows your TOTAL per asset (both wallets), while the pills inside still split per wallet, because a swap can only spend one wallet's money. The drawer's Assets tab gained a Normal Savings row (counted once — the Savings line, not the Assets line). Asset pages (/assets/XLM) now show the account TOTAL with a "who holds what" line. And the ⟳ "All wallets" button is gone: the wallet tabs show wallets, the "+" connects new ones — one control per job.

Part G — the live-test fallout round (2026-08-19)

What changed, in plain words: Niko's real BTC swaps exposed a family of "built for the fast chains" assumptions. Delivery ETAs now come from a per-chain settlement registry (BTC 10–60 min, ETH 1–5, SOL/Stellar 1–3) — one place to edit when a chain or bridge changes, no hardcoded copy. BTC swaps now track to TRUE delivery like SOL/ETH (the popup's Delivering step holds until the payout confirms, then waits for the balance refetch before Done). An expired Lobstr/WalletConnect session mid-flow now pauses and resumes the step (reconnect window opens by itself) instead of failing the swap. The Activity table gained: rows the moment a swap starts, correct per-flow statuses, no duplicate rows for hybrid swaps, and a reliable newest-first order. And the recovery banner now steps aside while the popup is actively working a transfer — but reappears instantly with its recovery button if anything goes wrong or the tab dies.
